### Chosen method

The connection method for this project is settled, not open for re-derivation by any agent reading this document. E0.1's exit criterion requires a primary method and a fallback to be named together with their known failure modes; this is that naming:

- **PRIMARY**: `godot-comprehensive`'s non-runtime tools (scene and node creation, script creation and validation, project settings), plus its sandboxed runtime bridge (see "Sandbox-only rule" below). It passed scene create/save/read-back and script create/attach/validate, both independently verified by reading the affected files back.
- **FALLBACK**: the Godot CLI directly (`Godot_v4.7.1-stable_win64_console.exe`, invoked with `--headless` for anything needing a process exit code). This is the functional fallback, not `godot-coding-solo`. Neither MCP server can run a headless script and return an exit code - confirmed against both servers' tool schemas, row 6 of the matrix - so the CLI is mandatory for exit-code work regardless of which MCP server is primary, and P0.7's gdUnit4 harness must use it. `godot-coding-solo` cannot substitute for this role, or for `godot-comprehensive`'s role: it has no live runtime bridge and no script create/attach/validate tools at all, confirmed by a direct tool-schema search of its live surface (rows 3 and 5 of the matrix). The CLI's known failure modes are recorded immediately below, in "Known failure modes and workarounds" - unlike the two MCP servers, it previously had none recorded here despite being the tool P0.7's harness is bound to.
- **NARROW, reduced trust, not the fallback**: `godot-coding-solo`. Its `add_node` reports success and logs `Save result: 0` while silently not writing the properties argument, verified by reading the saved `.tscn` back (row 2, finding F-07). Use it only for version and run operations; never trust its property writes, and do not treat it as standing in for either the primary or the fallback method.

### Known failure modes and workarounds

- **`add_node` property silence (godot-coding-solo, F-07)**: `add_node` returns a fully success-shaped response, including a logged property assignment and `Save result: 0 (OK=0)`, while the property is never written to the saved scene. Node and scene creation are reliable on this server; the `properties` argument is not. Workaround: pair any `godot-coding-solo` `add_node` call with an independent read-back of the saved file, or use `godot-comprehensive` for property-bearing node authoring.
- **Injected input: which call to use, and how to verify it (F-08, closed).** Input injection works. What does not work is polling `Input.is_key_pressed` after a key-parameter call, and the reason is the tool, not the engine. Established by reading the handlers in `tools/mcp/comprehensive/src/scripts/mcp_interaction_server.gd` and probing the running game: `game_key_press` with a `key` parameter calls `Input.parse_input_event`, then awaits one `process_frame` and sends a release, so any poll after the call reads false; `game_key_hold` with a `key` parameter sends no release, but the key state still did not persist and the probe found `DisplayServer.window_is_focused()` false, consistent with Godot clearing pressed input on focus loss in an MCP-launched window; `game_key_hold` with an `action` parameter calls `Input.action_press` and works - `Input.is_action_pressed` returned true with strength 1.0 and was still true 5829 frames later. Rule for P2.15 scripted bots: drive bots through INPUT ACTIONS, using `game_key_hold` with the `action` parameter and polling `Input.is_action_pressed`. Raw key events do reach `_input` handlers - a runtime probe counted two `InputEventKey` events, the second being the auto-release - so `_input`-based verification is also valid. An earlier version of this document stated a different root cause, that `parse_input_event` never updates the key-state array; that was reasoned rather than tested and a blind review disproved it on the pinned engine.
- **Port 9090 already in use (godot-comprehensive)**: a real listener bound to `127.0.0.1:9090` produced the in-engine error `Failed to listen on port 9090, error: 22` when `run_project` ran anyway; the game itself still launched and ran, but a dependent `game_*` call failed with a bounded 10-second timeout rather than hanging. Recovery: free the port and re-run; `stop_project` still tears down the orphaned game process normally.
- **Godot process killed externally mid-command (both servers)**: force-killing the live Godot process outside the tool layer was detected cleanly and immediately by both servers, each returning a clear "No active Godot process" style error rather than hanging. For `godot-comprehensive`, the injected autoload's cleanup (removing the `[autoload]` line and the `.gd` file from `project.godot`) still ran correctly under this abrupt kill, verified by an independent file read afterward.

**Godot CLI (fallback) known failure modes**, researched in `phases/PHASE_00_Environment_And_Connection/evidence/e01_control_paths.md`:

- **CRITICAL FOR P0.7 - gdUnit4 refuses headless by default unless both flags are passed**: gdUnit4's `runtest.cmd` will not run under `--headless` alone - it is refused "to prevent test errors that inevitably occur during UI tests, since Godot cannot process UI input in headless mode." Both `--headless` AND `--ignoreHeadlessMode` must be passed together, or the run does not happen at all. P0.7's harness is bound to the CLI (see "Chosen method" above), so this is not an optional detail: a gdUnit4 invocation in P0.7 that omits `--ignoreHeadlessMode` will not run, not merely run degraded. Workaround: use the invocation under "Verified gdUnit4 invocation, for P0.7" below. Do NOT use the addon's own `runtest.cmd` wrapper for CI. **The reason first recorded here was wrong, and the corrected reason is the opposite one** (Phase 01 finding F01-23): the wrapper passes neither `--headless` nor `--ignoreHeadlessMode`, and because it omits `--headless` it does not hit exit 103 at all - it was run directly and opens a window, initialises Vulkan, executes the suite and exits 0. Exit 103 arises only when `--headless` is passed *without* `--ignoreHeadlessMode`, which matches `GdUnitTestCIRunner.gd` gating on `DisplayServer.get_name() == "headless"`. So the wrapper's defect for CI is that it runs windowed on a machine that may have no display, not that it refuses to run. The advice is unchanged; only its stated cause is corrected, and the correction was reached by running the wrapper rather than by reading it. Confirm the gdUnit4 release and its 4.7.1 compatibility against the upstream releases page before P0.7 pins it, noting finding F-12 on the repository migration.
- **Godot 4.7.1 headless stall (issue #122707)**: reported to reproduce on Godot 4.7.1.stable.official on Windows 11 (and Linux/WSL2) - combining `--headless` with any loaded main scene plus a frame-count quit causes the process to stall after roughly 25-55 seconds, burning 20-30% CPU with almost no progress; closed upstream "not planned," no maintainer root cause given. The report notes that a `--script` overriding `MainLoop`/`SceneTree` directly, never going through Godot's normal "main scene" load path - exactly gdUnit4's own approach - does not exhibit the stall. Workaround: drive acceptance-test scripts through a custom `SceneTree`-derived `--script`, not Godot's normal "run main scene" path. E0.1's own recovered evidence ran a headless heartbeat past 2,040 frames with no stall in this project's sandbox, so the bug did not reproduce here on that one run; this does not rule it out for other scene shapes and is treated as a live risk, not a closed one.
- **`--export-release` exit-code misreporting history**: `SceneTree.quit(exit_code)` from `--script` was reported to be ignored entirely (always exited 0) in Godot 4.2.1/4.2.2 (issue #88055), said-fixed for 4.3 via PR #89229; `--export-release` itself has a recurring history of misreporting success or failure through its exit code across separate issues (#94957: exit 0 despite a failed C# build; #91527: export does not exit at all on a build error; #60258: unexpected SIGILL/132 on otherwise-successful exports in some CI setups). None of this was independently reconfirmed fixed for 4.7.1 in the research pass. Workaround: do not trust `--export-release`'s exit code alone; also scan stdout/stderr for an explicit marker string, and confirm empirically that a nonzero `quit(N)` actually propagates on this exact 4.7.1 build before depending on it for gating.
- **No screenshot capture under true `--headless`**: `--headless` disables all rendering, not only the window; off-screen `SubViewport`/render-to-texture is also disabled, there is no Windows equivalent of Linux's Xvfb workaround, and the one alternative Godot proposal (`--offscreen`) remains open, is explicitly incompatible with `--headless`, and still needs GPU access. Workaround: keep headless CLI work scoped to logic/state assertions and gdUnit4; route any screenshot or visual-evidence requirement through `godot-comprehensive`'s sandboxed `game_screenshot` on a real, windowed run instead.
- **Console vs. windowed binary confusion**: using the windowed `.exe` for `--script`/gdUnit4 work silently loses terminal stdout capture. Workaround: always invoke the console build (`Godot_v4.7.1-stable_win64_console.exe`) for any headless/CLI work; this project keeps both builds side by side for exactly this reason.

### Sandbox-only rule

`godot-comprehensive`'s `run_project` and every `game_*` tool are used only against `sandbox/connection_test`, never the real project (author decision). `run_project` injects a GDScript autoload (`McpInteractionServer`) into `project.godot` on every call, not opt-in, and opens a `127.0.0.1:9090` listener exposing `game_eval`, which compiles and executes arbitrary GDScript at runtime - architecturally equivalent to code execution under the account running Godot, since GDScript's `FileAccess`/`OS` APIs are not confined to the project directory. Its authoring tools (scene, node, script, project-settings work) do not inject anything and stay available for the real project. Mitigating evidence: the autoload injection's cleanup has been proven reliable across every scenario tested in this phase - a normal `stop_project` call, and an external force-kill of the Godot process (see above) - with the reverted `project.godot` verified by an independent file read after each. This is proven-reliable cleanup within what has been tested, stated as such rather than as a general persistence guarantee.

### Rebuild steps

Anyone rebuilding either server from scratch follows this order, confirming each step before moving on rather than assuming success:

1. `git clone` the server's repository into its real on-disk directory: `tools/mcp/coding-solo/` from `Coding-Solo/godot-mcp`, and `tools/mcp/comprehensive/` from `tugcantopaloglu/godot-mcp`. These are the actual directory names; `godot-coding-solo` and `godot-comprehensive` are the MCP server labels used in `.claude.json` and elsewhere in this document's prose, not the on-disk folder names, and cloning into `tools/mcp/godot-coding-solo/` or `tools/mcp/godot-comprehensive/` would not match what the pin-verification check below expects.
2. `git checkout <pinned-sha>` - the exact commit named above for that server.
3. `npm install`, which runs the package's `prepare` script and compiles TypeScript into `build/`.
4. Confirm `build/index.js` exists on disk before trusting the build.
5. Verify with an MCP `initialize` probe **before changing any config**: pipe a real MCP `initialize` request into `node build/index.js` over stdio and confirm a valid `protocolVersion` response comes back. Do not edit the MCP config on the strength of a successful build alone; prove the built server actually speaks MCP first.
6. Only then point the MCP config (outside this repository, e.g. `.claude.json`) at `command: node` with the absolute path to that server's `build/index.js`, preserving `GODOT_PATH` and every other configured server entry, and back up the config file before editing it.
7. Restart Claude Code - the pin takes effect only on restart - then re-verify with a live `get_godot_version` call and, if possible, by inspecting the running process's command line to confirm it points at the local build rather than any cached `npx` install.

### Pin verification check

`tools/mcp/**` is gitignored, and the MCP configuration outside this repository stores only a path, not a commit sha - so nothing in version control by itself proves the pin still holds. The exact check, to be run at each phase entry:

```
git -C tools/mcp/coding-solo rev-parse HEAD
git -C tools/mcp/comprehensive rev-parse HEAD
```

The first command's output must equal `1209744fad78f3998f98c7394fd0f6ef50da5281`; the second must equal `fcbc29e03297900b9a1fcc6c7cbae116fe9d532a`. Both `tools/.gdignore` and `sandbox/.gdignore` must also exist (as empty files - their presence, not their content, is what matters, per the CRITICAL note below). A mismatch on either commit, or either `.gdignore` file missing, means the pin or the export-packaging protection no longer holds and must be re-established before the phase proceeds.

For gdUnit4, which is committed rather than gitignored, the equivalent check is:

```
grep '^version=' addons/gdUnit4/plugin.cfg
find addons/gdUnit4 -type f | LC_ALL=C sort | xargs sha256sum | sha256sum
```

The first must report `version="6.2.1"`; the second must equal `5ae43377c9501520d2a6191c59e4e156aa3525ad4d9c69716db62e1d78ab8b9a`. A changed hash with an unchanged version means the addon was modified in place, which is the case a version string alone cannot catch. `.gitattributes` marks `addons/gdUnit4/** -text` so git never normalises the addon's line endings: without that, a clone on a machine whose `core.autocrlf` differs from this one would check out different bytes and the hash would fail for a correct copy.

**Also verify, at any phase entry that runs an export**, that the test surface is still excluded from the build. `export_presets.cfg` carries `exclude_filter="addons/gdUnit4/*, tests/*, reports/*, src/data/samples/*"` - the last arm added after a reviewer found the eleven placeholder contract fixtures shipping in the pack. Note that a `.gdignore` is the wrong instrument here and must not be used: inside `addons/gdUnit4/` it would hide the addon from the engine's own resource scanner and break the harness itself, which is why the `tools/`/`sandbox/` pattern below does not transfer to it. gdUnit4 also writes HTML and XML reports to `res://reports/` on every headless run; that directory is gitignored and export-excluded, and is safe to delete at any time.

### CRITICAL note for rebuilders: `.gdignore`

`tools/` and `sandbox/` each need an empty `.gdignore` file, because Godot treats everything under the project root as a resource and will otherwise pack the MCP servers - including their GDScript - into the exported game. Finding F-05: the first Windows release export of an empty scene packed `res://tools/mcp/...` into the game, producing an 11,229,568 byte (11.2 MB) `.pck`; adding `.gdignore` to both directories and re-exporting reduced it to 22 KB, and a byte search of the resulting pack found no MCP server code. Both `.gdignore` files live inside gitignored directories, so they are **not** in the repository and must be recreated by hand alongside any server rebuild.

## How the AI Collaborator Works Here

Sonnet subagents write documents and implementation; Opus runs critical agents and phase reviewers. At the review gate, both kinds of Opus reviewer receive `PLAN.md`, `LEDGER.md`, and the artifacts produced - they never see the implementer's reasoning, only what it produced and what the plan required.

### The same-commit rule

This document owns the rule that every commit changing a system's implementation also changes that system's document, per the Documentation Structure entry for document 28. Stated as an enforceable rule: no commit may change GDScript, scenes, resources, or project settings belonging to a system without also updating the document that owns that system in the same commit - with one exception: a change already specified by an existing document does not require that document to change. Implementing a value, layout, or behaviour the owning document already records is not itself a design change and introduces nothing new to document; the rule exists to catch undocumented decisions, not to force a document edit for every commit that merely executes what is already written.

This is checked by the per-task critical agents at each phase's review gate, who compare the commit history against the documents each task's Owner-doc column names as part of checking that task's real evidence against its plan steps. `phases/README.md`'s loop rule (c) states the critical agents' general duty (check each task against its plan steps and acceptance tests using real evidence, score it out of 10); it does not itself spell out this specific commit-versus-Owner-doc comparison, and this document should not be read as claiming it does. A commit that changes implementation with no matching documentation change, and no existing document already specifying the change, is a finding against that phase, not a silent pass.

**Checked against a real commit.** `bd65fd8` ("P0.2: Godot 4.7.1 project skeleton, Settings check passing") changes `project.godot`, `scenes/main.tscn`, `src/core/boot_check.gd`, and `tests/settings_check.gd`, with no change under `docs/`. This does not break the rule as stated with its exception: P0.2's Owner doc is docs/20, and every value the commit records - the 1920x1080 viewport, canvas_items stretch with keep aspect, the 60-physics-tick / max-8-step settings, the 16 collision layer names, vsync on - is a value docs/20 already specifies; the commit executes what docs/20 already recorded rather than deciding something new. This check was performed while correcting this document, not at a phase review gate, and should be read as a spot-check pending the phase's own review gate, not as that gate's finding.

### The review cadence

Execution follows the five-step supervised review loop defined in `phases/README.md` ("Loop rules"): pre-implementation (read prior phases' logs and carry forward applicable lessons), implementation (execute the phase plan, logging every action), review gate (per-task critical agents and one phase reviewer, all Opus, scoring against real evidence), fix and repeat (gather findings into the phase ledger, fix, re-review until the phase's bar is met or three iterations fail it), and close (update lessons and status, fold documentation and register changes back into the master and its docs, add a Change Log row). This document does not restate the loop's detail; `phases/README.md` is authoritative for it.

### The Gate Approval rule

Per MASTER_SDLC.md > Document Control > Gate Approval: only the human designer writes a gate row into the master's Change Log naming the gate and the date. An AI collaborator may propose that row's text but must never write it into the Change Log itself. No agent - Sonnet or Opus, implementer or reviewer - may write that a gate is passed, satisfied, met, or ready; that determination belongs to the designer and, ahead of the designer's decision, to the reviewers scoring evidence against the plan. A gate row does not change the master document's version number.

### Spot-check delegated output

Subagent reports are not accepted at face value. Phase 00's own record demonstrates why: an orchestrator spot-check of P0.3's output (26 generated documentation stubs, not taken on the subagent's word) found that all 26 omitted the trailing two-space line break after `**Version:**` that the five pre-existing drafts carried, a defect the subagent's own success report had not surfaced (finding F-01, fixed with a scripted pass verified file-by-file afterward). The same discipline applies to acceptance checks: every check that can pass must first be proven able to fail, rather than trusted on a single successful run. `tests/settings_check.gd` was first falsified twice, on a collision layer name and on `config/features`, and a reviewer then showed it still passed with exit 0 on a project whose whole display block was deleted and whose movement key was rebound, because both falsifications had hit assertions that were already the strongest while the rest asserted existence rather than value (finding F-10). Rewritten to assert effective values and exact sets, then falsified ten ways - rogue autoload, rogue action, features by equality, a mutated deadzone, a missing main scene, a rebound key, the display block, the autoload, and a Meta-modified rebind - each producing a named failure and exit 1. The lesson is to falsify against the assertion's own mechanism, not against whatever breaks most easily. `validate_script` was proven the same way during the connection-test matrix: run against a deliberately broken script, it returned `{"valid": false, "errorCount": 1}` with the exact line of the injected syntax error, rather than being trusted only on its passing runs against correct scripts.
