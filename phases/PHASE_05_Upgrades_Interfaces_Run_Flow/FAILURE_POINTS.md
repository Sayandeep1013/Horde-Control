# Phase 05 - Failure Points

## Predetermined

Restated from PLAN.md > "Predetermined failure points and risks".

| Risk | Why it might happen | Mitigation | Detection |
| --- | --- | --- | --- |
| A partial pause caused by a timer that does not run on SimClock | P2.12 (Draft), P2.13 (Console), and P2.14 (pause menu, focus loss) each introduce their own UI timers (hold-to-confirm fill rings, the Console's purchase channel, input lockouts); a Godot `SceneTreeTimer` or `Tween` left off PauseAuthority's control would keep advancing while the Draft or pause menu is open | Route every one of these timers through SimClock and PauseAuthority only (MASTER_SDLC.md > Risk Register: "Godot pause traps (SceneTreeTimer, Tween, PROCESS_MODE_ALWAYS leakage)"; banned APIs listed under Global Simulation Authority) | Pause authority test (full); Console non-pause test as the inverse check, confirming the Console's own channel timer keeps running under SimClock while the rest of the sim is not paused |
| The Draft auto-confirming a held input on open | If a player is holding the movement-only confirm direction, a gamepad stick, or a key at the exact moment a level-up opens the Draft, a hold-to-confirm path that arms immediately would confirm a card the player never chose | Implement the neutral-return arming rule exactly per docs/19_UI_UX.md > "Upgrade Draft UI & Navigation" > "Input Lockout & Arming": hold-to-confirm inputs arm only once input has returned to neutral at least once after the lockout ends | Draft input lockout test |
| The Console opening on radius entry alone and becoming a safe stop | A simpler implementation of P2.13 might open the Console the instant the player enters the Interaction Radius, turning the radius into a place to stand safely without needing to transact | Implement the Console's documented lifecycle exactly (docs/19_UI_UX.md > "Tower Console UI" > "Lifecycle": 0.3 s below 10% base speed inside the radius, at least one affordable entry); keep the player's auto-fire disabled at any speed while overlapping the radius regardless of whether the Console is open | Console rules test; Interaction window test (scripted), which checks that opening the Console during an active encounter still costs the player something |
| Upgrade pool produces a dominant build | P2.11's six upgrades and two fallback cards are a small pool; with only three ranks and shared ranks between channels, one upgrade could end up strictly better than the others at every rank | Cross-check each upgrade's per-rank effect against the others once all six are implemented, before Phase 05 review (MASTER_SDLC.md > Risk Register: "Upgrade pool produces a dominant build" - mitigation "Pool audit before every content milestone"); the full Dominant pair audit is a VS-tagged test out of prototype scope | Upgrade effect check confirms each upgrade applies its documented effect with no drift; a qualitative pool read is added to REVIEW.md for this phase since no prototype-tagged test measures dominance directly |
| Determinism / keyed RNG drift | P2.12's Draft offers and P2.10's earlier drop rolls both consume keyed RNG; if the Draft's card-offer roll is not keyed off the run seed and a stable counter (draft index, not wall-clock time or an object instance ID), replaying the same seed will not reproduce the same three cards | Key every Draft roll exactly per MASTER_SDLC.md > Provisional Values Register > Technical Caps & Performance > "Keyed RNG" (hash of run seed plus a named, stable counter), matching the pattern already proven for spawn and drop rolls in Phase 04 | Determinism test |

## Discovered during execution

| What happened | Cause | Fix | How to prevent it next time |
| --- | --- | --- | --- |
| Melee enemies could not damage the Tower at all, and every test of the attack cycle stayed green | The attack cycle gates on the Register's `reach_or_range_px` (20 px for a Tower Seeker), so an enemy stops and attacks out to 140 px from the Tower's centre, while the hitbox radius was hard-coded to `body_radius + 6 px` and can only overlap a 106 px Tower hurtbox within 126 px. A 14 px band in which the AI ran its wind-up on schedule and the two `Area2D` shapes never touched | The hitbox is now sized to `body_radius + max(reach, contact margin)`, so the physical shape's reach matches the logical gate's reach. Found by parking one real Seeker at a distance its own code reported as in-range, with the Tower's weapon disabled, and counting landed hits: zero over 240 ticks | **A logical range check and a physical collision shape are two different numbers and nothing makes them agree.** Assert that the physical shape covers the logical gate, or derive one from the other. Every attack, pickup, interaction and trigger radius in this project has this exposure |
| A plausible, confidently-stated hypothesis about that bug was wrong | P2.14 proposed that the Tower intercepted all twelve Seekers before any landed a hit, reasoning from the Tower's DPS against Seeker health. It never tested a single Seeker against a disabled Tower weapon | The integration task built the smallest scenario that could distinguish the two explanations and widened it by one variable | This project's standing rule - never write "root cause" without an experiment - was followed and it paid. Note that the wrong hypothesis was *reasonable*: plausibility is not evidence, and a measurement was cheap |
| Wave-spawned enemies had no Tower reference, so no Seeker could seek in real play | `set_tower_reference()` was called only for the three hand-placed enemies in the integration script, whose own header named that limit. The spawn path never called it | An enemy with no explicit reference now resolves the Tower through the EntityRegistry's `&"tower"` tag - the class fix rather than the instance fix, made possible by the debt pass registering the Tower there the same day | When a limit is named in a header rather than in the ledger, it is invisible to everyone who does not open that file. A named limit belongs in the ledger with an owner |
| The Console needed a code call, not a NodePath, and would have failed with no symptom | `RunInventory` is a `RefCounted`, so it cannot be an exported NodePath. Unwired, every Console entry reads zero Scrap and the Console dwell-detects, builds itself and never opens - no error, no warning | Wired in the integration pass, and now asserted by identity in `prototype_integration_test.gd` - the same object must reach the Console, the run-flow controller and the HUD | A dependency that cannot be expressed as a NodePath is the most likely one to be forgotten, because the scene file shows no gap. Assert the identity, not the existence |
| A falsification stayed green against the mutation it was written for | `console_rules_test.gd` declared its constants as `const X = Console.X`, reading the expectation back from the class under test, so zeroing the dwell moved the expectation with it | Rewritten as independent literals transcribed from the Register; the mutation then went red | Same shape as Phase 01's schema check asking the script under test what fields to expect. A test must never import its expectation from the code under test |
| The orchestrator's own fix for a reported Major had no test coverage at all | Five missing `_run_step()` dispatch calls were added from the symptom report. Removing one again left seven candidate suites green | Widened so that every one of the fifteen steps dispatches, with a suite that iterates the `Step` enum rather than a hand-written list | A fix applied by the orchestrator is falsified exactly like a delegated one; and a fix written against a single reported symptom tends to cover only that symptom |
| The integration agent was terminated mid-verification by an API session limit | A long-running task reached the account's session limit | Its artifacts were salvaged from disk and verified by reading the diff, rather than re-running the task. The three items it never reached are carried as named work | Phase 00 already recorded that an interrupted agent's artifacts are worth salvaging. What was missing here was the orchestrator budgeting the longest task last, when the remaining session was least certain |
