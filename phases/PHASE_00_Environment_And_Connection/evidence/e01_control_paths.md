## 1. Approach families covered

1. MCP servers that drive Godot through its command line (`godot-coding-solo` / `@coding-solo/godot-mcp`, `godot-comprehensive` / `github:tugcantopaloglu/godot-mcp` — both already configured for this project)
2. MCP servers / editor plugins that open a local TCP or WebSocket bridge into the running editor and/or game (mkdevkit/godot-mcp, ProtoForgeSystems/godot-claude-mcp, Erodenn/godot-mcp-runtime, slangwald/godot-mcp, Godot MCP Studio, Godot MCP Pro, plus the wider 2026 field of similar community servers)
3. Godot's own built‑in ports: GDScript language server (6005), Debug Adapter Protocol (6006), remote debugger (6007)
4. Headless command‑line runs: `--headless`, `--script`, `--export-release`, `--quit`, exit codes, gdUnit4
5. Newer (2026) approaches not covered above: GDExtension‑native bridges, a patched‑engine fork, EditorDebuggerPlugin‑native bridges, an in‑engine‑native MCP server, and the general shape the 2026 community has converged on

## 3. Family 1 — MCP servers driving Godot via CLI (already configured)

### 3.1 `godot-coding-solo` (`@coding-solo/godot-mcp`)

- **Observed tool surface (this session, 2026‑09‑17):** `add_node`, `create_scene`, `export_mesh_library`, `get_debug_output`, `get_godot_version`, `get_project_info`, `get_uid`, `launch_editor`, `list_projects`, `load_sprite`, `run_project`, `save_scene`, `stop_project`, `update_project_uids` — 14 tools, no script‑creation, no live scene‑tree/property/screenshot/input tools. `run_project`'s schema takes only `projectPath` and an optional `scene`; there is no headless flag.
- **License:** MIT. **Godot version:** not explicitly pinned; UID‑management tools imply Godot 4.4+ features. **Popularity/maintenance:** 5.7k GitHub stars (by far the most popular candidate researched), but no formal GitHub Releases page; latest npm publish is `0.1.1` (2026‑02‑03). GitHub `main` has commits past that npm publish, up to 2026‑04‑16, including a merge titled `fix/rce-arbitrary-script-instantiation` — **the published npm version is older than that fix.** (github.com/Coding-Solo/godot-mcp, registry.npmjs.org/@coding-solo/godot-mcp)
- **Known security history:** GitHub Issue #64, "Remote Code Execution via Unsanitized `projectPath`" — command injection via string‑concatenated `execAsync` calls, affecting `create_scene`/`add_node`/other `projectPath`‑taking tools; reported 2026‑01‑19, fixed via PR #67. (github.com/Coding-Solo/godot-mcp/issues/64)
- **Reliability on Windows:** unaudited beyond the above; being CLI/file‑based rather than a standing bridge, it likely avoids the "editor has the live TCP port open" class of failure but is exposed to the general Node‑on‑Windows path‑separator and npx‑cold‑start issues common to this whole family (see §8).
- **Operational cost:** addon‑free (no Godot‑side plugin to commit); version pinning is complicated by the npm/GitHub divergence noted above — pinning to "latest npm" is not automatically the safest choice.

### 3.2 `godot-comprehensive` (`github:tugcantopaloglu/godot-mcp`)

- **Observed tool surface (this session, 2026‑09‑17):** a very large surface (150+ tools visible in this session's tool list) spanning project/scene/script authoring (`create_scene`, `add_node`, `modify_scene_node`, `attach_script`, `create_script`, `create_csharp_script`, `save_scene`, `read_scene`), process control (`run_project`, `stop_project`, `export_project`, `manage_export_presets`), debug/log access (`get_debug_output`, `game_get_errors`, `game_get_logs`), **live runtime control** (`game_get_scene_tree`, `game_get_node_info`, `game_get_property`, `game_set_property`, `game_screenshot`, `game_key_press`/`hold`/`release`, `game_mouse_move`/`drag`/`click`, `game_gamepad`, `game_touch`, `game_input_action`), and a directly observed **arbitrary‑code‑execution primitive**, `game_eval` — schema: `{"code": "GDScript code to execute. Use \"return\" to return values."}`. This confirms the "another agent is auditing the source" caveat matters: this server is *not* purely CLI‑driving in practice — its `game_*` tool family is architecturally a live runtime bridge (family 2), even though the task places it in family 1.
- **License:** MIT. **Godot version:** README states Godot 4.4+, "tested and confirmed working with Godot 4.7" — directly relevant to this project's pinned 4.7.1. **Releases:** v3.1.0 (2026‑07‑13, "157 tools, Godot 4.4+ tested on 4.7"), v3.0.0 (2026‑07‑10), v2.0.0 (2026‑03‑02), v0.1.0 (2026‑02‑08); 459 stars. (github.com/tugcantopaloglu/godot-mcp, github.com/tugcantopaloglu/godot-mcp/releases.atom)
- **Known security history:** Issue #9, "Unauthorized Persistent Autoload Injection via Unrestricted `projectPath` in `run_project`" — insufficient validation (only blocked literal `..`) allowed absolute‑path injection of a malicious autoload containing a TCP listener + GDScript‑eval RCE primitive into any writable Godot project, persisting even if Godot failed to launch. Reported 2026‑05‑25, fixed via commit `eb63add` adding an opt‑in `GODOT_MCP_ALLOWED_DIRS` allowlist, closing related issues #11–#14, #16. v3.1.0 (2026‑07‑13) postdates the fix. (github.com/tugcantopaloglu/godot-mcp/issues/9, github.com/tugcantopaloglu/godot-mcp/commit/eb63add552aa4bd9205395cf91b40654654a3c)
- **Reliability on Windows:** unaudited beyond the above. `game_eval` and the live bridge tools imply an internal TCP/WebSocket channel similar to family 2's servers, so the same file‑lock/stdio/path‑separator caveats in §8 apply, plus the `GODOT_MCP_ALLOWED_DIRS` mitigation should be set to `D:\Gamedev` only once pinned.
- **Operational cost:** highest‑capability single tool in the whole survey for this project's stated needs, but also the largest attack surface (`game_eval`) and the most complex to keep version‑pinned safely (must pin to a release that includes the `eb63add` fix).

## 4. Family 2 — TCP/WebSocket bridge servers

### 4.1 mkdevkit/godot-mcp [1]

Node.js MCP server bridging to a Godot editor plugin over WebSocket, default port **6505** (`GODOT_MCP_PORT` overridable); editor‑side WebSocket server plus three runtime autoloads (`MCPRuntimeBridge`, `MCPInputBridge`, `MCPScreenshotBridge`) polling `user://` files for in‑game inspection/input/screenshots while the game is in Play mode. **Addon is committed to VCS** — install step is "copy `addons/godot_mcp/` into your project," no `.gitignore` guidance given. 173 tools across 26 categories claimed. States "Godot 4.4+" only, no explicit 4.7 statement. **License:** MIT. **Maintenance:** essentially inactive since June 2026 — 4 total commits (init/readme 2026‑05‑29, one change 2026‑06‑08, a FUNDING.yml 2026‑06‑09), no tags/releases, 14 stars. **Security:** no authentication documented on the WebSocket channel at all. Source: github.com/mkdevkit/godot-mcp (README, commits, tags, LICENSE).

### 4.2 ProtoForgeSystems/godot-claude-mcp [2]

A free, self‑hosted **Python** replacement for the paid Node.js relay normally bundled with the commercial product **godot-mcp-pro** (youichi-uda, $15 one‑time — see §4.6); it drives the *same* GDScript addon (`addons/godot_mcp/`) over the same protocol, `ws://127.0.0.1:6505` (localhost only). The addon itself must still be installed from the separate, **proprietary‑licensed** godot-mcp-pro repository — despite a secondary source describing it as "free, MIT‑licensed," the addon repo's own LICENSE/sidebar say "Proprietary." Documents ~16–20 tools: scene/node CRUD with undo‑redo, play/stop scene with screenshots, editor error/stack‑trace retrieval, camera control, and an `execute_editor_script` arbitrary‑GDScript tool gated by an opt‑in `allow_unsafe_editor_io` flag. States "Godot 4.x" only. **License:** this server is MIT. **Maintenance:** small (1 star) but recently active — commits through 2026‑08‑26. **Security:** no auth on the WebSocket connection beyond localhost binding; relies on a lock‑file/process‑scan scheme to avoid colliding `play_scene` calls across multiple open editors. Source: github.com/ProtoForgeSystems/godot-claude-mcp (README, LICENSE), github.com/youichi-uda/godot-mcp-pro (addon license).

### 4.3 Erodenn/godot-mcp-runtime [3]

The task's candidate that "advertises a transient‑autoload runtime bridge with no addon committed to version control" — **verified mechanically, and it is accurate.** Repository is canonically cased `Erodenn/godot-mcp-runtime` (lowercase in the prompt still resolves via GitHub's case‑insensitive routing). Mechanism (from `docs/architecture.md`): on `run_project`/`attach_project` the server **physically copies** `mcp_bridge.gd` into `.mcp/godot-runtime/bridge/` inside the target project and **writes a temporary autoload entry** into `project.godot`; both the `.mcp/` directory and the entry are auto‑added to `.gitignore`. On `stop_project`/`detach_project`, or automatically at session end, both the file and the autoload entry are removed — "Godot reads autoloads only at process start," so **it does not survive editor restarts by design** and is re‑injected fresh every session. Two modes: `run_project` (server spawns Godot) and `attach_project` (bridge injected, Godot launched separately, e.g. by CI). Distributed via `npx -y godot-mcp-runtime`. **Bind:** localhost‑only TCP, auto‑selected free port unless pinned via `bridgePort`. **Capabilities:** headless scene/node/script/signal editing and validation with *no editor window required*; screenshots (inline preview or PNG); input simulation (keys, mouse, UI‑element‑by‑name click, Godot input actions); UI‑tree discovery; live GDScript execution against the running scene tree; built‑in profiler access; a "background mode" (off‑screen window at ‑9999,‑9999) for less‑intrusive runtime sessions. States "Godot 4.x" only, no explicit 4.7/4.7.1 pin. **License:** MIT. **Maintenance:** by far the most active of the six named bridge candidates — 74 stars, 17 forks, 229 commits, a real release cadence (10+ tagged versions between roughly July and September 2026, most recently v3.7.0 on 2026‑09‑15), and merged external contributor PRs. **Security (documented in `docs/security.md`, the most thorough of any candidate reviewed):** per‑session token auth on the bridge channel (env var in spawned mode, baked into the injected script in attached mode) — explicitly described as stopping only "unauthenticated drive‑by" access, not a same‑machine attacker; a separate, unauthenticated profiler channel (first connection wins); a three‑tier static‑analysis gate on `run_script`/`run_project` GDScript execution (Tier 1 hard‑blocks dangerous calls like `OS.execute`, `Engine.get_singleton`, non‑literal `load`; Tier 2 prompts for user confirmation via MCP elicitation; Tier 3 executes with a warning) that the docs themselves call "a best‑effort accident guard, not a sandbox," with documented bypasses (token‑level not AST‑level matching, unscanned inline `.tscn` sub‑resource scripts); an env var (`GODOT_MCP_DISABLE_SECURITY`) can disable the whole gate, with the docs stating "an agent should decline to set it." Source: github.com/Erodenn/godot-mcp-runtime (README, `docs/architecture.md`, `docs/security.md`, LICENSE, releases, commits).

### 4.4 slangwald/godot-mcp [4]

Two localhost TCP sockets: **9500** (Editor Plugin — scene tree, run/stop, save, script attach, undo/redo, resource listing) and **9501** (Game Autoload — screenshots, mouse‑click simulation, live runtime scene‑tree inspection). JSON over TCP, base64 PNG for screenshots, short‑lived connect/send/receive/close connections. **Addon must be committed** — `addons/mcp_bridge/` plus a `mcp_bridge_game.gd` autoload. States **Godot 4.6 only**, explicitly — not stated for 4.7. **License:** MIT. **Maintenance:** early‑stage, low adoption (3 stars, 1 fork, ~10 commits, most recent early‑to‑mid Feb 2026), no tagged releases, includes demo projects (Kanban board, spinning cube, cookie clicker). **Security:** no authentication documented on either socket. Source: github.com/slangwald/godot-mcp (README, LICENSE, commits).

### 4.5 Godot MCP Studio (godotmcpstudio.com) [5]

**Real, live commercial product; closed‑source.** Publisher stated as "Coadite" (site footer explicitly disclaims Godot Foundation affiliation); a related free "Lite" build is separately distributed on itch.io by handle "soultel" — whether these are the same entity is **unverified**, no statement ties them together. **Editions:** Lite is free, no account, "60 focused tools" per one part of the site and "77 tools" per another (**internally inconsistent claim, flagged**); Pro is a one‑time paid purchase (€39 promo rising to €59 on a stated Nov 4 date, year unstated), plus separate paid image‑generation credit packs for an "Image Studio" add‑on. **Claims:** live scene tree, errors, and screenshots through a local bridge; player‑input simulation; two permission modes — "Safe Edit" (default, confirmation required before deletes/code execution) and "Full Control." **Technical detail undisclosed:** no port numbers, no protocol name, and no Godot‑version compatibility statement found anywhere on the site or its troubleshooting docs — the addon lives at `addons/godot_mcp_studio/` and must be enabled with the editor open. **Platform:** Windows and macOS only (no Linux). **Independent corroboration:** essentially absent — one PulseMCP listing that surfaced in search under a similar name actually points to an unrelated GitHub repo (noise, not corroboration); an "Awesome MCP Servers" listing could not be fetched (HTTP 403); no forum threads, reviews, or security notes were found. **Verdict:** looks like a real, functioning small commercial tool (working docs site, specific and plausible technical claims, a free itch.io tier) rather than vaporware, but it is closed‑source, has an internally inconsistent capability claim, undisclosed port/protocol/Godot‑version details, and no independent security review. Source: godotmcpstudio.com, godotmcpstudio.com/docs/troubleshooting, soultel.itch.io/godot-mcp-studio-lite.

### 4.6 Godot MCP Pro (Godot Asset Library / youichi‑uda) [6]

Asset Library listing (asset 4961, submitted 2026‑08‑03; license field "Proprietary"), also distributed on itch.io. **Hybrid open/closed model:** the public GitHub repo (`youichi-uda/godot-mcp-pro`) contains only the free Godot‑side editor plugin (`addons/godot_mcp/`); the actual Node.js MCP server (`server/`) is **not in the public repo** and is sold separately, $15 one‑time via itch.io / Buy Me a Coffee with "lifetime updates." **Claims:** 162–175 tools (count is inconsistent across the Asset Library page, GitHub description, and README) across 23 categories — project, scene, node, script, editor, input, runtime, animation, 3D scene, physics, particle, navigation, audio, TileMap. **Architecture:** AI client → Node.js server → Godot editor plugin over **WebSocket, primary port 6505, auto‑scan fallback 6510–6514**. Multiple tool‑set modes (Full/3D/Lite/Minimal) to fit different MCP clients' tool‑count limits. **Godot version:** 4.4+ explicitly stated. Requires Node.js 18+. **Maintenance:** the most community traction of any bridge candidate researched — 599 stars, 76 forks, 7 open issues, 78 commits (exact last‑commit date unverified). **Security‑relevant, explicit by design:** `execute_editor_script` and `execute_game_script` tools intentionally run arbitrary GDScript; the WebSocket port has **no documented authentication**; a referenced `SECURITY.md` could not be retrieved in this pass (unverified content). **Notable buyer caveat:** paying for "Pro" gets a proprietary server component not in the public repo, so "open‑source" only accurately describes the free editor‑side half. Source: godotengine.org/asset-library/asset/4961, github.com/youichi-uda/godot-mcp-pro, y1uda.itch.io/godot-mcp-pro.

### 4.7 The wider 2026 field (context for family 2, not separately audited)

The 2026 community has converged heavily on this same architecture — a GDScript `EditorPlugin` exposing a local WebSocket/TCP bridge, paired with an external Node.js/Python MCP process. Notable, more‑independently‑verified entrants surfaced during "newer approaches" research (§6) but architecturally belong here: **satelliteoflove/godot-mcp** (upstream original many forks derive from; MIT; 165 stars; 311 commits; last push 2026‑09‑16; deterministic playtesting via freeze/step of game time; Godot 4.5+), **hybridindie/godot-mcp** (explicitly refuses to bind non‑loopback without `GODOT_MCP_AUTH_TOKEN` set — a stronger default security posture than most; Godot 4.4 min, 4.7 recommended), and **Godot MCP Toolkit** (store.godotengine.org/asset/npgamedev/godot-mcp-toolkit — per‑project session tokens; Godot **4.2 through 4.7 explicitly stated**, the most precise 4.7 compatibility claim found for any bridge‑style server in this whole survey). See §6 for the full long‑tail list.

## 5. Family 3 — Godot's built‑in ports

All three are **editor‑side** services (configured via `EditorSettings`, not `project.godot`) that exist only while a Godot editor process (including `godot --headless --editor`) is running, and all three default to binding **127.0.0.1 only**, with **no authentication mechanism** in any of them per source inspection. (docs.godotengine.org/en/stable/tutorials/editor/external_editor.html; github.com/godotengine/godot, various files cited below)

### 5.1 GDScript language server — default port 6005

Standard **LSP** over TCP. Settings: `network/language_server/remote_host` (default `127.0.0.1`), `network/language_server/remote_port` (default `6005`), plus `enable_smart_resolve`, `show_native_symbols_in_editor`, `use_thread`, `poll_limit_usec`; CLI override `--lsp-port <port>`. **What it gives an external client:** code completion, diagnostics, symbol lookup/hover, go‑to‑definition on GDScript — **nothing else**; no scene editing, no run/debug capability (this is exactly why Godot separately built DAP — see godot-proposals#2494). **Known consumers:** VS Code's official "Godot Tools" extension, Emacs `lsp-mode`/`eglot` via `emacs-gdscript-mode`, Neovim configs, coc.nvim, and a couple of stdio‑bridge wrappers for CLI agents since the LSP is TCP‑only, not stdio. Source: docs.godotengine.org/en/stable/tutorials/editor/external_editor.html, docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html.

### 5.2 Debug Adapter Protocol — default port 6006

Standard Microsoft **DAP** over TCP (`editor/debugger/debug_adapter/debug_adapter_protocol.cpp`). Settings: `network/debug_adapter/remote_port` (default 6006, no `remote_host` override — host is hardcoded to loopback), `request_timeout`, `sync_breakpoints`; CLI `--dap-port <port>`; requires "Debug with External Editor" enabled in the Script view. **What it gives an external client:** breakpoints (set/verify/clear), step over/into/out, continue/pause, stack trace and scoped variable (Locals/Members/Globals) inspection, runtime expression evaluation. **Documented gap:** a third‑party DAP‑based MCP server (`TransitionMatrix/godot-dap-mcp-server`) states `godot_set_variable` is "currently disabled due to upstream Godot limitation" — i.e., **writing a variable's value through DAP is not reliably supported**, unverified against an authoritative Godot source. **Known consumers:** VS Code Godot Tools (`launch.json` → `debugServer`); the dedicated `TransitionMatrix/godot-dap-mcp-server` MCP bridge. **Known bugs:** immediate disconnect before project boot (godot/issues/108518), a Windows‑specific path‑mismatch bug (godot/issues/75834). Source: github.com/godotengine/godot/blob/master/editor/debugger/debug_adapter/debug_adapter_server.cpp, docs.godotengine.org/en/stable/tutorials/editor/external_editor.html.

### 5.3 Remote debugger / remote scene‑tree protocol — default port 6007 (script/print output on 6006)

**Not a published/standard protocol** — a Godot‑proprietary binary/Variant‑serialization protocol (`core/debugger/remote_debugger.cpp`, `scene/debugger/scene_debugger.h`); a godot‑docs issue explicitly requesting a guide for it remains open (godot-docs/issues/11245). Settings: `network/debug/remote_host` (a UI dropdown of local interfaces, not a free‑form 0.0.0.0 option per a recent doc correction — godot/pull/98282, godot/issues/99063), `network/debug/remote_port` (historically buggy, resets to 6007 regardless of configured value — godot/issues/87566); CLI `--remote-debug <uri>` / `--debug-server <uri>`; "Keep Debug Server Open" toggle. **Source‑level inspection of `scene_debugger.h` confirms the wire protocol genuinely implements everything this project would want**: `_msg_request_scene_tree` (read live tree), `_msg_inspect_object(s)` (read properties), `_msg_set_object_property` (**write a property live**), `_msg_live_create_node`/`_msg_live_remove_node`/`_msg_live_reparent_node`/`_msg_live_node_call` (live scene editing), `_msg_rq_screenshot` (**screenshot**), `_handle_input`/`_handle_embed_input` (**input injection**). **However**, no official documentation describes this as a stable, versioned public API — the only documented consumer is the editor's own "Remote" tab ("inspect or change the nodes' parameters in the running project" — docs.godotengine.org/en/stable/tutorials/scripting/debug/overview_of_debugging_tools.html), and no independently verified open‑source tool was found driving the *full* read/write/screenshot/input surface externally; the one example found, `LeeSinLiang/godot-mcp`, connects to 6006/6007 **only** to capture print/error/warning text output, not to read/write scene state. **Security history:** CVE‑2019‑10069 — unauthenticated, network‑exploitable RCE (CVSS 9.8) via incorrect deserialization policy in the debugger protocol on Godot through 3.1, fixed 3.2‑stable‑1 (cvedetails.com/cve/CVE-2019-10069, strix.ai/cve/CVE-2019-10069); **no Godot‑4.x‑specific CVE was found, but whether the underlying deserialization path has been hardened since was not independently re‑audited here** — flag as unverified if this protocol is ever driven directly. A Godot contributor discussion explicitly frames enabling remote debug as opening "a network reachable port" (godot/pull/99428, godot-proposals/issues/11191); it is loopback‑only by default and requires deliberately reconfiguring `remote_host` plus a firewall rule to reach across machines. **Windows notes:** Godot prompts to add itself to the Windows Firewall on first run; a tracked issue notes firewall entries don't distinguish Godot versions (godot/issues/26249); a documented port‑reuse bug ("Error listening on port 6007" after a prior session didn't release the port) exists (godot/issues/41650).

## 6. Family 4 — Headless command‑line runs

### 6.1 Flags, exit codes (docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html unless noted)

- `--headless` = `--display-driver headless --audio-driver Dummy`; "disables all rendering and window management functions." Available in release builds; required on GPU‑less machines; on Windows it also suppresses a window popping up during export.
- `--script <path>`: runs a `SceneTree`/`MainLoop`‑derived script; **"extended"** (editor builds / export templates built with `disable_path_overrides=false` only).
- `--export-release <preset> <path>` / `--export-debug`: extended/editor‑build only.
- `--quit`: quit after first iteration. `--quit-after <N>`: quit after N iterations.
- **Exit codes:** `SceneTree.quit(exit_code)` overrides the process exit code (0–125 valid range) — but `OS.set_exit_code()` was **removed** from the API, so a bare `MainLoop` script (not `SceneTree`) cannot set one directly without instantiating a temporary `SceneTree` (godot/issues/90646, archived proposal). **Historical bug:** `SceneTree.quit(exit_code)` from `--script` was ignored entirely (always exited 0) in Godot 4.2.1/4.2.2, filed as #88055, said‑fixed for 4.3 via PR #89229 — **not independently reconfirmed for 4.7.1 in this research; verify empirically in the sandbox.** `--export-release` similarly returned exit code 0 on failure in 4.1.2 (#83042, fixed for 4.3 via PR #89234), but related exit‑code‑unreliability reports recur in different forms afterward (#94957 — 0 despite a failed C# build; #91527 — export doesn't exit at all on a build error; #60258 — unexpected SIGILL/132 on otherwise‑successful exports in some CI setups). **Net: do not trust `--export-release`'s exit code alone; also scan stdout/stderr.**

### 6.2 What headless mode cannot do

`--headless`'s own definition disables *all* rendering, not just window display — most `RenderingServer`/`DisplayServer` calls return dummy values (godot/blob/master/servers/display_server_headless.h). **Off‑screen SubViewport/render‑to‑texture is also disabled**, not only the window — this is the entire reason a still‑open `--offscreen` proposal exists specifically as an *alternative to*, not a companion of, `--headless`, and it still requires GPU access (godot-proposals/issues/5790). **No screenshot capture is possible in true headless mode**, and there is no native Windows equivalent of Linux's Xvfb virtual‑framebuffer workaround (windowsforum.com/threads/windows-equivalent-of-xvfb.250675) — the only path to a real rendered screenshot on Windows is a non‑headless run. Audio is forced to a no‑op `Dummy` driver. Programmatic input simulation (`Input.action_press`, `Input.parse_input_event`) works at the API level but gdUnit4's own docs warn synthesized events "do not travel in a headless engine" for some UI paths.

### 6.3 Full scene tree / physics / autoloads / game loop for scripted acceptance tests

In principle physics, `_process`/`_physics_process`, timers, signals, and autoloads are *not* rendering‑server operations and should keep functioning headlessly; this composite claim is well‑supported by the mechanics above but **is not stated as one explicit guarantee in a single official doc** — treat as reasonably reliable, not officially certified. **Directly relevant, version‑specific finding:** GitHub issue #122707, filed 2026‑08‑21, reproduces on **Godot 4.7.1.stable.official on Windows 11** (and Linux/WSL2): combining `--headless` with any loaded main scene plus a frame‑count quit causes the process to **stall after ~25–55 seconds**, burning 20–30% CPU with almost no progress; the main thread stays alive but worker threads go idle. The reporter notes a `--script` that overrides `MainLoop`/`SceneTree` directly and never goes through Godot's normal "main scene" load path — i.e., exactly gdUnit4's own approach — **does not** exhibit the stall. Closed "not planned," no maintainer root‑cause given — **treat as unverified beyond the report itself, and reproduce a throwaway repro in the E0.1 sandbox before relying on headless main‑scene runs for gating.**

### 6.4 gdUnit4 (moved to `godot-gdunit-labs/gdUnit4`, formerly `MikeSchulze/gdUnit4`)

Headless invocation is via `addons/gdUnit4/runtest.cmd` on Windows (wraps `addons/gdUnit4/bin/GdUnitCmdTool.gd`), requiring `GODOT_BIN` set to the Godot executable (console build recommended, matching this project's own harness convention). CLI flags: `-a/--add`, `-i/--ignore`, `-c/--continue`, `-conf/--config`, `-rd/--report-directory` (default `res://reports/`), `-rc/--report-count`. **Headless is refused by default** — "to prevent test errors that inevitably occur during UI tests, since Godot cannot process UI input in headless mode" — both `--headless` *and* `--ignoreHeadlessMode` must be passed to force it. **Exit codes are documented and specific:** `0` = all tests passed, `100` = test failures, `101` = test warnings. Produces both an HTML report and a **JUnit‑compatible `results.xml`**, suitable for CI ingestion. **Godot 4.7/4.7.1 compatibility is explicitly stated** in the README's compatibility table for the `master` branch (internal tag v6.2.1) and the tagged `v6.2.0` release; `v6.1.x` tops out at 4.6.3. The exact current release version/date could not be pinned with full confidence in this pass — one extraction suggested a date that conflicts with 4.7 not existing yet at that time, so **re‑check github.com/godot-gdunit-labs/gdUnit4/releases directly before citing a version in P0.5/P0.7.** Source: godot-gdunit-labs.github.io/gdUnit4/latest/advanced_testing/cmd/, raw.githubusercontent.com/godot-gdunit-labs/gdUnit4/master/README.md.

## 7. Family 5 — Newer (2026) approaches

### 7.1 Official Godot Foundation position — the opposite of a new tool

No Foundation‑owned MCP server, no AI‑agent API in 4.x, no godot‑proposals issue for MCP/agent tooling was found. The one directly relevant official item is the **Godot contribution policy update, 2026‑06‑30** (godotengine.org/article/contribution-policy-2026): *"No autonomous AI agent use or vibe coding,"* which *"already leads to an auto‑ban from our GitHub repository,"* AI *"should be limited to menial things (like code completion, regex, or find and replace),"* and use *"must [be] disclose[d] in the PR discussion."* **Scope is contributions to the `godotengine/godot` engine repository itself — it says nothing about end users driving their own project with an agent**, which is what this task is about, but it is worth recording as a policy signal and a reason not to expect first‑party tooling. Caveat for the sandbox test: at least one third‑party project brands itself misleadingly as the *"Official Plugin for the Godot Engine"* (`bebabinlarsson-blip/Godot-MCP`) while being unaffiliated — Asset Library listing is not endorsement.

### 7.2 Anthropic/Claude‑specific

No Anthropic‑published Godot skill, plugin, or announcement was found; `site:anthropic.com Godot` returns nothing. Of the two skill candidates named in `NEXT_SESSION.md` Prompt 3 (full audit is that prompt's job, not this one): **Randroids‑Dojo/Godot‑Claude‑Skills** contains no MCP server itself but documents *requiring* a **custom Godot engine fork**, `Randroids-Dojo/godot` (`automation` branch) — see §7.4, a genuinely distinct mechanism worth flagging to whoever runs Prompt 3. **alexmeckes/godot-claude-skills** resolves to a companion bridge, `alexmeckes/godot-mcp` (WebSocket, port 6550, loopback, **no auth token** documented) — this is a variant of family 2, not a new mechanism.

- **GDAgent** (store.godotengine.org/asset/gdagent/gdagent) — ships three compiled binaries (`gdagent.dll` terminal GDExtension, `godot_mcp.dll` MCP GDExtension server, `gdagent-mcp.exe` bridge helper) that embed terminal AI agents (Claude Code, OpenCode, Codex) **inside the editor**. ### 7.4 Patched‑engine fork extending the native remote‑debugger protocol

**Randroids‑Dojo/godot** (`automation` branch) + **Randroids‑Dojo/PlayGodot** — the single most architecturally distinct finding in this whole survey. It is a **modified Godot engine build** (patches `core/debugger/remote_debugger.cpp`) that extends the stock RemoteDebugger wire protocol (family 3, §5.3) with new automation commands (`get_node`, `get_property`, `set_property`, `call_method`, `screenshot`, `scene_tree`, `pause`, `time_scale`), driven by a Python client styled as "Playwright for Godot" connecting via `godot --path <project> --remote-debug tcp://127.0.0.1:6007`. **It controls a running game, not the editor.** MIT, 38 stars. **Stale**: PlayGodot's last push is 2026‑02‑24; the automation branch tip is commit `a8cacb6` dated **2026‑01‑27** (a later repository‑level "pushed_at" timestamp reflects unrelated branches, not this one). **Highest operational cost of any approach surveyed** — it requires building and maintaining a non‑stock Godot binary tied to a specific engine patch, which this project's rule of pinning to the official 4.7.1 release directly conflicts with.

### 7.5 EditorDebuggerPlugin‑native bridges (distinct from the raw DAP/remote‑debugger ports)

Godot 4.x's scripting‑accessible `EditorDebuggerPlugin`/`EditorDebuggerSession` APIs let an addon hook the editor's own debugger session (breaked/output/debug_data signals) without spawning a separate subprocess or re‑implementing the wire protocol. **dsh‑godot‑tool** (github.com/Fromlan/dsh-godot-tool) does this: `addons/agent_rpc/rpc_debugger.gd` extends `EditorDebuggerPlugin` to capture runtime errors into a 50‑event ring buffer, alongside a loopback‑only, newline‑delimited‑JSON TCP channel (port 8765, fallback 8774) with a 32‑hex‑digit auth token, 27 `godot_*` tools. MIT, 11 commits, last push 2026‑08‑15. **Notably: its README explicitly states it was "tested on Godot 4.4 stable and 4.7 stable (Windows)"** — one of the very few candidates in this entire survey with a direct, dated Windows‑4.7 test claim. It targets a "DeepSeek Harness" rather than Claude Code specifically, so would need adaptation. A second project, **dcc-mcp/dcc-mcp-godot**, reportedly uses the same EditorDebuggerPlugin + EngineDebugger pattern so operations execute in the game process rather than the editor process (163–164 tools, MIT) — this could not be independently verified beyond a secondary search summary in this pass.

### 7.6 In‑engine‑native MCP server (no external process)

**Godot MCP Native** (store.godotengine.org/asset/yurineko73/godot-mcp-native) — distinct because the MCP server itself is implemented **inside** Godot rather than as an external Node/Python process: streamable HTTP MCP endpoint at `http://localhost:9080/mcp`, optional `auth_token`, headless‑style launch via `godot --editor --path <p> -- --mcp-server` with `--mcp-port=N`. 155 tools (71 debug‑category). States Godot **4.0–4.8** (4.6 minimum). MIT, free, v1.0.8 (2026‑07‑30, marked unstable by its own author).

### 7.7 Computer‑use / vision‑based OS control

**Explicitly empty for Godot** — no project or writeup was found driving the Godot editor via OS‑level screen‑reading + click/keystroke automation (no PyAutoGUI/Windows UI Automation/Anthropic computer‑use pattern applied to Godot). The closest adjacent finding, `godot-agent-vision` (part of `thedivergentai/gd-agentic-skills`, LGPL‑3.0, Godot 4.7+, 718 stars), only scores screenshots against a rubric for self‑verification — it explicitly warns *"NEVER ship the editor bridge as an Autoload or leave `addons/gdskillsagentvision/` committed"* — and does not drive input. A second‑hand blog pattern (vivecuervo7.github.io/dev-blog/p/claude-code-godot) uses screenshots only for self‑verification while actual control flows through a **file‑based `.cmd-queue`/`.cmd-result` IPC pair** plus direct `.tscn`/`.gd` text edits — a distinct, low‑tech control pattern (no network port at all) worth naming as an option, though not independently verified here.

### 7.8 The dominant 2026 DIY pattern, and its security‑norm shift

By volume, the community has converged on one shape: a GDScript `EditorPlugin` exposing scene‑tree/property/eval access over a local socket, paired with an external Node.js/Python MCP process translating tool calls. Transport is most often WebSocket (ports vary wildly and have no convention: 6505, 6550, 8000/9500 split‑hop, 8765, 8766, 9080, or reuse of stock 6006/6007); message format is JSON, often explicitly **JSON‑RPC 2.0**. **The security norm visibly shifted during 2026** from "localhost binding is the only protection" (still common — mkdevkit, ProtoForgeSystems, slangwald, alexmeckes' bridge, satelliteoflove, godot‑devtool) toward **localhost + a per‑session random token** written to a local file the paired server reads (Erodenn/godot-mcp-runtime, `Aesthetic-Engine/godot-runtime-bridge`, `Glade-tool/glade-mcp`, dsh‑godot‑tool, Godot MCP Toolkit, hi‑godot/godot-ai, hybridindie/godot-mcp which explicitly refuses a non‑loopback bind without a token set). One project states the honest limit of this model plainly: *"possession of the raw bridge token grants bridge access; this is not a sandbox against other processes running as you"* (Noa3/GodotMCP).

**Long tail — named but not independently opened in this pass** (roundup/SEO‑sourced, second‑hand, listed for completeness only): KeeVeeG godot‑mcp, GodotIQ, Godot Sentinel MCP, AKDworks Godot‑Clarity, Glade‑tool/glade‑mcp, 3ddelano/gdai‑mcp‑plugin‑godot, IvanMurzak/Godot‑MCP (C#, cloud‑connected, Apache‑2.0), bradypp/godot‑mcp, SrDarkoll/godot‑mcp, mcintalmo/godot‑engine‑mcp, n24q02m/better‑godot‑mcp, ee0pdt/Godot‑MCP, PiMPStudios/Claude‑GoDot‑MCP, Dokujaa/Godot‑MCP, **Farraskuy/Godot‑MCP** (no license file — public source, not open‑source licensed), **tomyud1/godot-mcp** (Asset Library asset 4767, 75 tools, MIT), **Ziva** (store.godotengine.org/asset/ziva/ziva — proprietary, $0–$200/mo subscription, includes screenshot analysis of the running game), **wangdiandao/godot-devtool** (MIT, 90 stars, default port 8766, includes UndoRedo‑safe editor mutations).

## 8. Reliability, security, and operational cost — cross‑cutting synthesis

### 8.1 Windows‑specific failure classes that recur across nearly every MCP‑style candidate

- **File locks / stale state while the editor GUI is also open.** Any tool that writes `.tscn`/`.gd` text directly (rather than driving the running editor process to make the change) can desync from Godot's own `.godot/` import cache and UID cache if an interactive editor window has the same project open; Godot may show "resource changed externally" or silently keep stale state. Applies to both configured servers and essentially every family‑2 candidate.
- **Windows path separators.** Node.js/Python servers built cross‑platform routinely mishandle the boundary between Windows‑native paths (`D:\Gamedev\...`) and Godot's `res://`‑style forward‑slash resource paths; a wrong separator surfaces as "resource not found." None of the researched projects' docs specifically call out Windows path handling as solved — treat as a standing risk to test explicitly in the sandbox.
- **stdio buffering / silent hangs.** Servers that read a spawned Godot process's stdout for debug output can appear to hang if that process buffers output (worse on the non‑console Windows build); this project already keeps a console build beside the windowed one specifically for this reason — any chosen method that reads debug output should be pointed at the console `.exe`.
- **`npx` cold start.** Any server invoked via `npx -y <package>` (e.g., Erodenn/godot-mcp-runtime) triggers a registry fetch on an uncached first run, adding latency and requiring outbound network access — which conflicts with this project's "network calls still ask" rule unless pre‑cached. After the first run, npm's local cache makes subsequent starts fast, but Windows Defender can add further delay by scanning freshly downloaded packages.

### 8.2 Security posture, compared

- All three **built‑in Godot ports** (LSP/DAP/remote debugger) bind loopback‑only by default and have **no authentication whatsoever** — their safety currently rests entirely on nothing else being able to reach 127.0.0.1, which is true for a single‑user Windows 11 desktop but worth stating plainly since it's a structural property, not a designed‑in protection. The remote debugger protocol has one historical critical CVE (CVE‑2019‑10069, pre‑3.2) for its deserialization path; not independently re‑audited for 4.x here.
- **Both already‑configured servers** have had, and fixed, `projectPath`‑driven RCE/path‑injection bugs (Coding‑Solo #64; tugcantopaloglu #9) — this is not unique to them; it is a recurring bug *shape* across this whole ecosystem (unsanitized path parameters reaching a shell/autoload‑injection sink), and pinning exact versions (P0.5) must specifically confirm the pinned release/commit is at or after each fix, not just "latest."
- **`godot-comprehensive`'s `game_eval` tool is a directly observed, first‑party‑confirmed arbitrary‑GDScript‑execution primitive** in this project's own configured tool surface — functionally equivalent to the "execute_editor_script"/"run_script" primitives that third‑party bridge servers gate behind confirmation prompts or static‑analysis tiers (Erodenn, ProtoForgeSystems). This project's `.claude/settings.json` currently gates `delete_file`, `export_project`, `manage_docker_export`, `manage_ci_pipeline`, `game_http_request`, and `game_websocket` under `ask` — **`game_eval` is not currently in that list** and arguably should be, once the sandbox test confirms the tool is actually reachable and useful.
- Among the six family‑2 candidates named in the task, only **Erodenn/godot-mcp-runtime** documents session‑token auth plus any code‑execution gating (explicitly self‑described as "not a sandbox"); **Godot MCP Pro** and (implied) **Godot MCP Studio** are the two candidates that are either partly or fully closed‑source, which conflicts with this project's stated rule to "install a bridge addon that a server needs only after reading its code."

### 8.3 Operational cost of keeping each family working

| Family | Addon in VCS? | Version pinning | Engine‑version coupling |
|---|---|---|---|
| Configured CLI servers (family 1) | No addon; server itself needs pinning | Must pin past the known RCE fixes (§3.1, §3.2); npm/GitHub can diverge | Loosely coupled (uses Godot CLI/editor APIs, not internal engine patches) |
| Family‑2 bridge servers (general) | Usually yes (addon copied into `addons/`), except Erodenn (transient, `.gitignore`'d) | Most have no tagged releases at all (mkdevkit, slangwald) or inconsistent tool‑count claims across their own docs (Studio, Pro) | Most state only "Godot 4.x" or "4.4+"; only Godot MCP Toolkit and dsh‑godot‑tool make an explicit, dated 4.7 claim |

| Headless CLI (family 4) | N/A | N/A | Perfectly coupled; gdUnit4 needs its own version tracked separately against Godot's (README compatibility table) |

## 9. Recommendation

**Primary method: `godot-comprehensive` (`github:tugcantopaloglu/godot-mcp`), already configured.** It is the only candidate in this entire survey — including every paid or closed‑source option — that already covers essentially the full capability matrix this project needs in one already‑approved, MIT‑licensed tool: scene/script authoring (`create_scene`, `add_node`, `attach_script`, `create_script`, `modify_scene_node`, `save_scene`, `read_scene`), process control (`run_project`, `stop_project`, `export_project`), debug output (`get_debug_output`, `game_get_errors`, `game_get_logs`), and — confirmed by direct inspection of its live tool schemas in this session, not marketing copy — a genuine runtime bridge (`game_get_scene_tree`, `game_get_node_info`, `game_set_property`, `game_screenshot`, `game_key_press`/`mouse`/`gamepad`/`touch`/`game_input_action`, `game_eval`). Its README states explicit testing against **Godot 4.7**, matching this project's pinned 4.7.1. It requires installing nothing new (already configured and allowed in `.claude/settings.json`), which satisfies "do not install software outside the project." Its one disclosed vulnerability class (autoload‑injection RCE, issue #9) has a published fix (`eb63add`, adding `GODOT_MCP_ALLOWED_DIRS`) that predates the current release tag (v3.1.0, 2026‑07‑13) — P0.5 should pin to v3.1.0 or later and explicitly set `GODOT_MCP_ALLOWED_DIRS` to `D:\Gamedev` only.

**Fallback method, two‑part:**

1. **`godot-coding-solo` (`@coding-solo/godot-mcp`), already configured**, for the subset of tasks it covers — scene/node creation, saving, running the project, and debug‑output capture — if `godot-comprehensive`'s larger tool surface or its live bridge component fails to connect. It is the most popular single project found in this whole survey (5.7k stars) and has its own published RCE fix (PR #67), but note the npm/GitHub divergence: pin to a version confirmed to include the `fix/rce-arbitrary-script-instantiation` commit, not simply "latest npm," and treat it as a narrower fallback since it exposes no live scene‑tree/property/screenshot/input tools at all (confirmed by its observed tool list) — it cannot substitute for `godot-comprehensive` on the "inspect and drive a running game" and "take a screenshot"/"inject input" requirements.
2. **Godot's own built‑in headless CLI (`--headless --script`, and gdUnit4's `runtest.cmd`), independent of either MCP server**, for everything this project needs that an MCP server round‑trip is the wrong tool for: running gdUnit4 with documented, specific exit codes (0/100/101) and JUnit XML output. This is not really competing with the two MCP servers above — it is required regardless of which is primary, because neither configured server exposes a headless flag on `run_project` (confirmed by direct schema inspection: both take only `projectPath` and an optional `scene`), so neither can be trusted to produce a guaranteed, code‑bearing, display‑free run. P0.7's harness requirement is satisfied by this path alone.

**Why not any family‑2 third‑party bridge as primary or fallback:** none improves materially on what `godot-comprehensive` already provides for this project, and each adds real cost — most (mkdevkit, slangwald, ProtoForgeSystems) state only "Godot 4.x"/"4.4+"/"4.6 only" compatibility with no 4.7 confirmation and no or minimal authentication; the two paid options (Godot MCP Studio, Godot MCP Pro) are partly or fully closed‑source, conflicting with the project's own rule to read a bridge addon's code before installing it even into the sandbox; and the best‑engineered of the six named candidates, **Erodenn/godot-mcp-runtime**, while genuinely impressive (session‑token auth, tiered code‑execution gating, transient no‑VCS‑footprint injection, active maintenance), would be adding a second live‑bridge dependency on top of one (`godot-comprehensive`) that already does the same job and is already approved — it is worth keeping in mind as a second‑line fallback to test in the E0.1 sandbox only if `godot-comprehensive`'s `game_*` bridge layer turns out not to work reliably on this machine.

### Known failure modes and workarounds

**`godot-comprehensive` / `godot-coding-solo` (MCP servers, Node.js over stdio, bridging into Godot):**

1. *`npx`/first‑run network dependency and latency* — if not pinned to a locally installed/cached version, a cold start can attempt an npm‑registry fetch, conflicting with the project's "network calls still ask" rule. **Workaround:** pin exact versions per P0.5 and install once so subsequent launches run from local cache, not the registry.
2. *File‑lock / stale state if a human also has the editor open* — direct `.tscn`/`.gd` writes plus a live editor window can desync the import/UID cache. **Workaround:** keep the interactive editor GUI closed during agent‑driven sessions; if it must be open, force an `EditorFileSystem` rescan / project reload before trusting editor‑visible state.
3. *Windows path‑separator mismatches* — backslashed Windows paths vs. `res://` forward‑slash resource paths can produce false "not found" errors. **Workaround:** always pass `projectPath` as the documented absolute Windows form; independently verify returned resource paths use `res://` forward slashes before chaining further calls.
4. *stdio buffering hides debug output* — the non‑console Windows Godot build can buffer stdout, making `get_debug_output` look empty on a live process. **Workaround:** point `GODOT_PATH` at the console build (`Godot_v4.7.1-stable_win64_console.exe`, already present beside the windowed one) for any workflow depending on debug‑output capture; poll with a timeout rather than a single blocking read.
5. *`game_eval` is a real code‑execution surface* — directly confirmed in this session's tool schema. **Workaround:** add `game_eval` (and any other arbitrary‑execution tool confirmed reachable in the sandbox) to the `ask` list in `.claude/settings.json`, alongside the existing gated destructive/export/network tools.
6. *Known, fixed RCE‑class bugs specific to these two projects* (Coding‑Solo #64; tugcantopaloglu #9). **Workaround:** when pinning exact versions for P0.5, explicitly confirm the pinned release/commit is at or after each fix — do not assume "latest npm" automatically includes the most recent GitHub fix, since Coding‑Solo's npm `0.1.1` is confirmed older than an April‑2026 GitHub‑only RCE fix commit; set `GODOT_MCP_ALLOWED_DIRS` (tugcantopaloglu) to `D:\Gamedev` only.
7. *No headless flag on `run_project`* (confirmed by direct schema inspection on both servers). **Workaround:** never rely on either server's `run_project` for CI/gating; use the independent headless CLI path (below) for anything needing a guaranteed exit code or no display server.

**Headless CLI + gdUnit4 (independent, always‑available path):**

1. *Godot‑4.7.1‑specific headless stall* (issue #122707, reproduced on Windows 11 on exactly this engine version) when `--headless` is combined with a loaded main scene and a frame‑count quit. **Workaround:** drive acceptance‑test scripts through a custom `SceneTree`‑derived `--script` that loads/instantiates scenes itself (the same pattern gdUnit4 already uses), not Godot's normal "run main scene" path; reproduce a throwaway repro in the E0.1 sandbox before depending on headless main‑scene runs for gating.
2. *Exit‑code reliability history* — `SceneTree.quit(exit_code)` from `--script` ignored the code entirely in 4.2.1/4.2.2 (said‑fixed for 4.3+, not independently reconfirmed for 4.7.1); `--export-release` has a recurring history of misreporting success/failure via exit code. **Workaround:** trust gdUnit4's own documented 0/100/101 codes (that's its contract), but for any hand‑rolled `--script` acceptance test, additionally scan stdout for an explicit marker string as a second signal, and confirm empirically in the sandbox that a nonzero `quit(N)` actually propagates on this exact 4.7.1 build.
3. *No real screenshot capture is possible under true `--headless` on Windows* (no Xvfb equivalent; the only official path, `--offscreen`, is explicitly incompatible with `--headless` and still needs GPU access). **Workaround:** keep headless CLI scoped to logic/state assertions and gdUnit4; route any screenshot/visual‑evidence requirement through `godot-comprehensive`'s `game_screenshot` on a real (windowed) run instead.
4. *gdUnit4 refuses headless by default* (to avoid UI‑input test errors) unless both `--headless` and `--ignoreHeadlessMode` are passed. **Workaround:** use the documented `runtest.cmd` wrapper with `GODOT_BIN` pointed at the pinned console build, rather than hand‑assembling the flag combination; confirm the exact current gdUnit4 release and its 4.7.1 compatibility claim directly against `github.com/godot-gdunit-labs/gdUnit4/releases` before pinning in P0.5/P0.7 (the repo has moved from `MikeSchulze/gdUnit4`).
5. *Console vs. windowed binary confusion* — using the windowed `.exe` for `--script`/gdUnit4 work silently loses terminal stdout capture. **Workaround:** always invoke the `_console.exe` build for any headless/CLI work; this project already keeps both builds side by side per `NEXT_SESSION.md`.
