## Real defects found and fixed during this task's own work

Recorded per this project's convention (self-caught defects are worth more than ones found later), all fixed and re-verified green before being reported:

1. **The final wave sat in an unreachable GAP state.** `_end_current_wave()` originally always transitioned to `State.GAP` and set an 8 s deadline, even for the final wave — which has no next wave to delay. `test_final_wave_never_ends_on_maximum_duration_but_ends_when_live_count_reaches_zero` caught this (state stayed `"GAP"` instead of `"SEQUENCE_COMPLETE"` one tick after the live count reached zero). Fixed by special-casing `_current_wave_index >= waves.size() - 1` to go straight to `SEQUENCE_COMPLETE`.
2. **A GDScript lambda-capture bug, twice.** `total_spawns: int` and `completed: bool`, each incremented/set inside a `.connect(func...)` lambda in `wave_sequence_test.gd`, silently mutated a captured *copy* rather than the outer variable — the assertions kept reading the original value (`0`, `false`) no matter how many times the signal fired. This is `gdscript-patterns`' own documented pitfall ("Lambda's change to a variable is lost — Locals are captured by value — Keep shared state in a member, Array or Dictionary"), hit for real rather than read about. Fixed by wrapping both in a one-element `Array` (a reference type, mutated in place).
3. **A test-order bug matching the project's own documented seam.** `WaveDirector._ready()` snapshots `_enemy_lookup` from the exported `tower_seeker_scene`/`player_hunter_scene`/`opportunist_scene` fields at `add_child()` time; assigning those fields afterward (the normal test pattern) does not retroactively update the snapshot. Two of the three new test files already called the existing `rebuild_lookups_for_test()` seam after assignment; `wave_sequence_test.gd`'s `before_test()` initially did not, producing a real engine error (`push_error("... no PackedScene wired ...")`) the moment the suite ran. Fixed by adding the missing call.
4. **A `push_error` that fired on every correctly-written test.** `WaveDirector._ready()` originally logged an error whenever `_entity_spawner` was still null at the end of `_ready()` — which is true for every test using this project's own `set_entity_spawner_for_test()` convention (called *after* `add_child()`, exactly like every other component's test seam in this codebase). This tripped the project's F02-14 engine-error guard on an otherwise fully green run. Fixed by removing the `_ready()`-time check and adding a lazy, one-shot warning inside `physics_step()` itself, which fires only if the director is genuinely asked to do work while unconfigured — a real misconfiguration signal, not a normal test-injection artifact.
5. **A geometry test that could never have passed, caught before trusting its result.** The first version of `test_shift_rescues_a_first_candidate_rejected_by_the_interaction_radius` built its candidate on a ring centred *on the Tower itself* — but every point on such a ring is, by construction, the same fixed distance from the Tower regardless of bearing, so no angular shift could ever change whether it is inside the Interaction Radius. The test's own setup-assertion failed immediately, before any falsification was attempted. Re-derived around an off-centre ring (the *real* in-scope case: the view ring when the camera sits near the Tower), which is also the only scenario in which this Register rule is ever reachable during actual play.
6. **Orphan node leak.** `PackedScene.pack(template_node)` copies the subtree into the resource but does not take ownership of `template_node` itself; every test's lightweight dummy-enemy-scene builder leaked one `Node2D` at teardown until `template_node.free()` was added after packing.

## Named acceptance test — Spawn ring test (P2.8)

`tests/unit/spawn_ring_test.gd`, 8 cases, split into two layers (see the file's own header for why): `SpawnGeometry` tested directly and statistically (1000 candidates, varied camera/ring positions) for the literal pass condition ("no enemy instantiates inside the camera view margin or the Interaction Radius"), plus deterministic edge cases for the shift-on-first-rejection behaviour (camera view, then Interaction Radius, each isolated), the arena-inset rule, the no-valid-point case, and the 8-consecutive-tick escalation's full-ring search; then `WaveDirector` end to end with a real `EntitySpawner`/`EntityRegistry` confirming a Tower Seeker lands on the Tower ring and a Player Hunter lands on the view ring.

**Falsification.** Mutated `SpawnGeometry.is_outside_camera_view()`'s comparison operators (`>` → `<`, inverting the exclusion), confirmed the 1000-candidate test failed loudly (dozens of "landed inside the camera view + 64 px margin" failures logged with exact positions), restored from a byte-identical backup (`md5sum` match, `diff -q` clean), re-ran green (8/8, exit 0).

## Wave-runtime suite (task-required)

`tests/unit/wave_sequence_test.gd`, 3 cases, run against the **real** preloaded 8-wave prototype sequence (not a throwaway scenario): (1) the sequence opens `wave_t1` → `wave_t2` → `wave_t3` → `wave_t4` → `wave_combat_1` → `wave_combat_2` → `wave_combat_3` → `wave_combat_4` in that exact order, with the gap after each of the first 7 waves matching `max(wave default, closing encounter's recovery gap)` — 5.0, 5.0, 8.0, 10.0, 8.0, 10.0, 8.0 seconds — within a 0.75 s tolerance (3× the 0.25 s test step); (2) no spawn group starts during an inter-wave gap, tracked via a running total across the `enemy_spawned` signal (not `get_spawned_count_for_test()`, which reflects only the *current* wave's own list); (3) the final wave never ends on its (deliberately tiny, 1 s) maximum duration, only once `EntityRegistry.get_live_enemy_count()` reaches zero.

Every enemy scene in this suite is a lightweight dummy `PackedScene` (bare `Node2D`, no `EnemyController`) — nothing ever fights or dies on its own, so every non-final wave ends on its authored maximum duration, which is exactly what makes the gap arithmetic checkable without a combat resolution system.

**Falsification.** Mutated `_end_current_wave()`'s gap formula from `maxf(wave.inter_wave_gap_seconds, encounter.minimum_recovery_gap_seconds)` down to `wave.inter_wave_gap_seconds` alone (dropping the encounter-recovery-gap floor). Confirmed the sequence test failed on exactly the three gaps where the dropped `max()` term actually mattered (after T3: 5.0 s reported vs. 8.0 s expected; after T4: 8.0 vs 10.0; after combat_2: 8.0 vs 10.0 — the other four gaps were unaffected, since their two terms already agreed, which is itself informative: this falsification could only ever be caught by a test that checked *every* gap, not a spot check). Restored (`diff -q` clean), re-ran green (3/3, exit 0).

## Determinism check (task-required)

`tests/unit/wave_determinism_test.gd`, 2 cases, against a throwaway three-encounter scenario (Siege, Split Assault, Hunt — one of each directional-weighting branch) so the check exercises more than the uniform case: (1) two independent pipelines (separate `EntityRegistry`/`SimClock`/`EntitySpawner`/camera, nothing shared) with the same `run_seed` produce byte-identical spawn positions in the same order; (2) a different `run_seed` changes at least one position — the falsification-style test this project's own rule requires ("a check must be able to fail"), included because a director that silently ignored `run_seed` (or drew from an unseeded engine RNG) would pass test (1) *vacuously*.

**Falsification, and it demonstrated exactly the failure mode test (2) exists to catch.** Mutated the primary spawn-placement RNG call from `KeyedRng.rng_for([run_seed, "spawn", serial])` to `KeyedRng.rng_for([0, "spawn", serial])` (hardcoding the seed root, discarding `run_seed`). Result: `test_same_seed_produces_identical_spawn_positions_in_order` **still passed** (vacuously — two runs of the same, now-ignored, seed obviously still agree), while `test_a_different_seed_changes_at_least_one_spawn_position` **failed** ("every spawn position was identical across two DIFFERENT seeds"). This is the intended, useful result: the mutation is only visible through the second test, which is exactly why both exist rather than only the first. Restored (`diff -q` clean), re-ran green (2/2, exit 0).

## Cross-task seams

1. **`src/core/sim_loop.gd` step 13 ("Wave Director") is still an empty stub**, and `src/core/` is outside this task's write scope — the same structural gap every prior P2.x task has recorded for its own SimLoop step (LEDGER F03-09/F03-22). `WaveDirector` exposes `physics_step(delta)` publicly and honours `driven_externally` (default `false`), matching `player.gd`'s and `enemy_controller.gd`'s own exact convention, so the future SimLoop integration task has a uniform seam.
2. **The Tower is not registered with `EntityRegistry`** (already on record, F03-26) — `WaveDirector` reads a live Tower's position/Interaction Radius through the same `tower_path`/`set_tower_reference()` seam `enemy_controller.gd` already established, with a Register-cited fallback (`arena_center`, `tower_definition_for_interaction_radius_fallback`) when none is wired, rather than inventing a third pattern.
3. **The orchestrator must supply three `PackedScene` references** (`tower_seeker_scene`, `player_hunter_scene`, `opportunist_scene`) and, ideally, a live camera (`camera_path`/`set_camera_reference()`) — without a camera, view-ring placement falls back to `arena_center` and a 1920×1080 reference size, which is honest but not representative of the real, moving camera. Wiring these three scene exports is the one thing that turns this director from "tested in isolation" into "actually spawning the game's real enemies."
4. **`EnemyController`'s own `_ready()` self-registers with `EntityRegistry`** using whatever `global_position` the node has at that moment (typically the scene's own default transform, not the spawn point) — `EntitySpawner.spawn_enemy()`'s own registration call is therefore a no-op (the entity is already registered by the time it runs). `WaveDirector` compensates by setting `instance.global_position` and explicitly calling `EntityRegistry.update_position()` immediately after acquiring the instance, so the registry's cached position is correct from the very first tick rather than one frame late. Named because it is easy to assume `spawn_enemy()`'s own position argument alone is sufficient — for a real `EnemyController`, it is not.
5. **`EntitySpawner`/`Pool` never reparent an acquired instance when no container is wired** (`entities_container_path` unset) — every test in this task's own suites relies on this (matching `entity_cap_test.gd`'s precedent) and explicitly frees spawned instances via `EntitySpawner.clear_all_for_test()` in `after_test()` rather than leaking them.
