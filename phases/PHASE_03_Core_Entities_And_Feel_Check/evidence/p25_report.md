## Cross-task seams

1. **The Tower is not registered with `EntityRegistry`.** Confirmed by reading every file under `src/tower/`: unlike the player (`player.gd` registers itself under `&"player"`), `tower.gd` never calls `EntityRegistry.register_entity()`. Tower Seekers and Opportunists therefore cannot find "the Tower" via any registry query. Worked around with `EnemyController.set_tower_reference(tower)` (a typed command) and an `@export tower_path` fallback, mirroring `tower_weapon.gd`'s own `origin_path` seam for the identical class of gap. Every test in this task's suites wires this explicitly; the real integration task (whoever assembles `scenes/main.tscn`) needs to call `set_tower_reference()` once, or extend `tower.gd` to self-register (outside this task's scope either way).
2. **The Enemy Definition Contract has no fields for the leash rule, the Opportunist event rule, the body-block window, or the stuck-rule numbers.** Worked around with `src/enemy/enemy_ai_tuning.gd`/`.tres`, deliberately placed under `src/enemy/` (unrestricted by this task's write scope) rather than `data/enemies/` (restricted to the three named `EnemyDefinition` instances) or `src/data/` (extending `enemy_definition.gd` itself was out of scope). 3. **`EntityRegistry` has no "add a tag to an already-registered entity" command.** A Hunter that converts to a Tower Seeker must re-register (deregister, then register with `[&"enemy", &"tower_seeker"]`) rather than mutating its existing registry entry in place. Not a defect — `register_entity()`/`deregister_entity()` is a complete, sufficient API for this — but worth naming since a future task adding a fourth or fifth dynamic tag would hit the same reregistration pattern.

## Real defects found and fixed during this task (not falsification near-misses — genuine bugs)

1. **`AttackSlotManager` crashed on teardown with freed references.** `EnemyController._exit_tree()` calls `AttackSlotManager.release_claim(_tower, self)` etc.; gdUnit4's cross-test node cleanup order is not guaranteed, so `_tower`/`_player`/`_opportunist_target` can already be a *freed* instance by the time `_exit_tree()` runs. Godot's argument-passing rejects a freed instance against a statically-typed `Node2D` parameter *before* the callee's own body runs — an `is_instance_valid()` guard as the function's first line cannot help, because the crash happens at the call boundary. Fixed by retyping every `AttackSlotManager` public parameter that could receive a stale reference from `Node2D` to `Variant`, with `is_instance_valid()` checks inside. Reproduced via `stuck_exemption_test.gd`'s own multi-entity teardown; SCRIPT ERROR text: `Invalid type in function 'release_claim'... (previously freed) is not a subclass of the expected argument class`.
2. **A real stuck-tracking bug that despawned enemies the instant an exemption ended.** `_update_stuck_tracking()`'s exempt branch called `_clear_stuck_episode()` (which resets `_stuck_episode_start_time` to a `-1.0` sentinel) and then immediately re-seeded *only* `_progress_reference_time` to a valid, current value — leaving the two fields inconsistent. The instant exemption ended, the "cold start" branch was skipped (since `_progress_reference_time` was no longer negative), and `_stuck_seconds = now - _stuck_episode_start_time` computed `now - (-1.0)`, a value that instantly exceeded the 20s despawn threshold. A queued enemy that finally got a free attack slot, or a body-blocked Seeker the instant the player moved away, would have been despawned on the very next tick. Found via `stuck_exemption_test.gd`'s own "did not claim the newly freed attack slot" failure, traced through several rounds of instrumented debugging (see the file's own extended commentary). Fixed by never touching `_stuck_episode_start_time` except at genuine cold-start or genuine-progress moments (`_clear_stuck_episode()` alone, letting the next tick's real cold-start branch re-anchor both fields together); the same pattern was also present and fixed in the "real progress made" branch, which had the identical latent bug.
3. **A real leaked-node bug in three of this task's own test suites.** Every fresh `SimClockScript.new()` instance created for fast-forwarding was never wrapped in `auto_free()` (unlike the established precedent in `tower_health_recovery_test.gd`, which does). Reproduced as a `WARNING: Detected 1 possible orphan nodes` on every affected test, extensively bisected (ruled out `move_and_slide()`, registry queries, and iteration count as causes) before finding the actual leaked object was the loose `SimClock` instance itself. Fixed by wrapping every occurrence in `auto_free()` across `leash_test.gd`, `opportunist_test.gd`, and `stuck_exemption_test.gd`.
4. **A real `SimClock.now`-based test-setup bug in `enemy_tag_registration_test.gd`.** `hunter.set_leash_deadline_for_test(SimClock.now - 1.0)` used the real `SimClock` Autoload; early in a fresh test process `SimClock.now` can be smaller than 1.0, making the computed deadline *negative* and colliding with `EnemyController`'s own `_leash_deadline < 0.0` "leash not tracked" sentinel — silently disabling the leash timer the test meant to force. Fixed by injecting a fresh `SimClock` instance started at `100.0` for this specific arithmetic, leaving the Tower's own real-clock-driven weapon untouched.
5. **A rounding-precision bug in the shared `_advance`/`_tick` test helpers.** `int(round(seconds / step))` could overshoot a threshold the test was deliberately trying to stay short of (a `0.48` request could resolve to `0.5` exactly). Replaced with `int(floor(seconds / step + 0.0001))` everywhere (four occurrences across three files) — floors instead of rounds, with a small epsilon so exact multiples are not accidentally floored down by floating-point noise.
6. **A test-construction bug in `opportunist_test.gd`'s out-of-range test.** The Tower was moved only 1000px away; the Opportunist's own chase speed (224 px/s) closed enough of that gap within the test's own 2.8–3.1s tick window to fall back inside the 400px aggro range before the "3 continuous seconds outside range" condition could ever complete, defeating the test's own premise. Fixed by moving the Tower 3000px away in both affected tests, far enough that the chase movement can never close the gap back under 400px within the ticked window.

## What each intent's implementation does, briefly

- **Tower Seeker**: fixed target (the Tower, via `set_tower_reference()`); attack-slot steering around the Tower's footprint; melee wind-up/hit cycle (0.4s wind-up, 1.5s cycle, 15 dmg) that also lands on the player whenever body-blocked (same physical hitbox, mask includes both hurtboxes, no separate "attack the player" code path needed); body-block detection (2s window, <8px progress, player within reach) which is *also*, by construction, the entire body-block stuck-exemption mechanism via the shared `in_attack_range` check; no secondary target, so its own 3s stuck fallback is direct approach.
- **Player Hunter**: fixed target (the player, via the `&"player"` `EntityRegistry` tag); Contact attack type (no wind-up, exempt per docs/09), 0.5s tick, 8 dmg, hitbox mask excludes the Tower entirely; leash timer (20s to telegraph, +0.5s to convert), reset on every landed hit; live conversion to a full Tower Seeker on the same node/instance (preserves HP, re-tags with `EntityRegistry`, swaps every stat via `_apply_definition()`); `is_finisher` flag exempts Overtime finishers from the leash entirely, per docs/09, though nothing in this task's scope spawns one yet.
- **Opportunist**: sticky target memory (`_opportunist_target`), picked at spawn by footprint-edge-adjusted distance; three event triggers (damaged by the other target's faction, 3 continuous seconds outside 400px aggro range, current target dies) all funnelling through one `_opportunist_reevaluate()` procedure; 25%-closer + 3s-lockout hysteresis gate, bypassed only when the current target is confirmed dead; its own 3s stuck fallback switches to the other target (bypassing the hysteresis gate, since that gate exists to stop flip-flopping between two *live* comparably-attractive targets, not to block an un-sticking manoeuvre) — a named interpretation, since docs/09 does not spell out this specific interaction.
