## The registration API (src/core/sim_loop.gd)

- `enum Step` names all fifteen steps (`INPUT` through `UI_STATE`). Only steps 2 (`PLAYER_MOVEMENT`), 3 (`ENEMY_AI_AND_MOVEMENT`), 4 (`WEAPON_TARGETING_AND_FIRING`), 5 (`PROJECTILE_MOVEMENT_AND_SWEEP`), 6 (`WINDUP_AND_CONTACT_TICKS`), and 13 (`WAVE_DIRECTOR`) have a registrant path wired by this task.
- `register(step, node) -> bool` / `unregister(step, node) -> bool`: `register()` refuses a null/freed node or one with no `physics_step(delta)` method (`push_error`, then `false`), and refuses double-registration at the *same* step (the same node at two *different* steps is allowed and is never exercised by this task's own wiring). Each accepted registration gets a monotonically increasing `reg_serial`, never reused even if the node later unregisters and re-registers.
- **Ordering rule, documented in the file:** same-step entries run in ascending order of (1) `EntityRegistry`'s own serial for that node, **if EntityRegistry exposes one** — checked via `_entity_registry.has_method(&"get_registration_serial")` — else (2) `reg_serial` (registration order). **`EntityRegistry` does not expose `get_registration_serial()` today** (confirmed by reading `src/core/entity_registry.gd` in full; it is out of this task's write scope). Branch (1) is therefore unreachable against the real Autoload in the shipped build; it exists so a future addition to `entity_registry.gd` needs no change on the SimLoop side. `tests/unit/sim_loop_registration_test.gd::test_same_step_order_prefers_an_injected_entity_registry_serial_over_registration_order` proves the branch is live code by injecting a fake registry via `set_entity_registry_for_test()`, not dead code — this is disclosed, not hidden, the same way this project has previously named provably-unreachable clauses (LEDGER F03-23).
- **No in-place mutation during iteration:** `register()`/`unregister()` never mutate the `Array` currently stored at `_registrations[step]`; each call produces a fresh `Array` (`duplicate()` + append/remove_at) and only then replaces the dictionary entry. `_run_step()` itself takes its own `duplicate()` snapshot before sorting and iterating. A register/unregister call made from inside another node's own `physics_step()` this same tick (an enemy unregistering itself on death, a node registering a new child) therefore cannot corrupt the in-progress pass; the change takes effect starting the next time that step runs. Proven by `test_a_node_unregistering_itself_mid_step_does_not_skip_or_duplicate_others` and `test_a_node_registered_mid_step_is_not_called_until_the_next_tick`.
- **Freed-node safety:** `_run_step()` checks `is_instance_valid(node)` immediately before calling `physics_step()`, skipping (never calling) an entry whose node was freed or removed since it registered.
- `get_combat_serial(subject)` is a **separate** counter/map from the registration-order one, answering a different question (docs/20's step-7 sort key: player = 0, Tower = 1, everything else assigned ascending on first sight). It accepts either a live `Node` (special-cased by class: `is Player` → 0, `is Tower` → 1) or a value tag (`String`/`StringName`, matching the project's existing "source resolved by value" convention for projectiles — `&"player"`/`&"tower"` also resolve to 0/1).
- `enqueue_hit()` gained three **optional, backward-compatible** trailing parameters (`target_hurtbox`, `attacker_node`, `on_hit_accepted`, all defaulting to null/empty). `sim_loop_order_test.gd`'s own pre-existing call with the original four positional arguments is unchanged and still exercises the sort in isolation, resolving to a no-op (nothing to apply damage to).
- `_step_07_hit_queue_resolution()` still sorts with the unmodified `_hit_less_than` comparator, then calls a new `_resolve_one_hit()` per record: applies damage via `target_hurtbox.receive_hit(attacker_node, amount, source)` (re-checking `is_dead` **at resolution time**, which is what carries the existing ghost-hit guarantee across the move from immediate to queued resolution), then calls `on_hit_accepted` only if the hit was accepted.

## How hitbox.gd / player_projectile.gd reach the SimLoop instance

SimLoop is a scene node, not an Autoload, so there is no global symbol for the *running instance* the way there is for `EntityRegistry`/`SimClock`. `SimLoop._ready()` calls `add_to_group(&"sim_loop")`; `hitbox.gd`, `player_projectile.gd`, and `enemy_controller.gd` each resolve `get_tree().get_first_node_in_group(&"sim_loop")` from a `call_deferred()`-scheduled method, not from `_ready()` directly. This is load-bearing, not stylistic: under `Main`, `Entities` (and therefore every enemy under it) finishes its whole `_ready()` pass **before** `SimLoop` ever runs its own (`Entities` is declared before `SimLoop` in `main.tscn`'s child list), so a same-frame, non-deferred lookup from an enemy's `_ready()` would always find nothing. Deferring past the point where the whole tree's `_ready()` calls have completed (but before the next physics tick) resolves this without depending on sibling order. Each file also exposes `set_sim_loop_for_test()` for direct injection, following this project's existing pre-ready-injection convention.

## A wrong turn, corrected before it reached the report

My first implementation set `driven_externally = true` directly in `scenes/player.tscn` (Player and AutoWeapon), `scenes/entities/tower_seeker.tscn` / `player_hunter.tscn` / `opportunist.tscn`, and `scenes/prototype.tscn`'s `WaveDirector` node. Running the full suite immediately surfaced real regressions: `leash_test.gd::test_landing_a_real_hit_on_the_player_resets_the_leash_timer`, `player_movement_test.gd` (multiple), and `player_input_buffer_test.gd::test_buffer_holds_the_last_direction_immediately_after_release` all instantiate `player.tscn` / `player_hunter.tscn` directly and rely on the scene's own default (`false`, self-driven) to exercise the real `_physics_process()` via `await get_tree().physics_frame`, with no SimLoop anywhere in their own tree to drive them instead. Baking `driven_externally = true` into the shared scene files silently stopped these entities from ever stepping in those tests.

Fixed by reverting every `.tscn` change and instead having `prototype_integration.gd` flip `driven_externally = true` **at runtime**, only on the specific instances it wires (`_player`, `_auto_weapon`, `_wave_director`, and each of the three hand-placed enemies in `_enemies`), immediately before registering them. Timing works because the whole scene's `_ready()` chain runs bottom-up and synchronously, and `PrototypeIntegration` is the scene root, so its `_ready()` (where the flag is set) runs *last* in that chain — before any deferred call (including `enemy_controller.gd`'s own deferred registration check) has fired. Confirmed by re-running the full suite: the three regressions cleared and no scene file carries any diff (`git diff --stat -- scenes/` is empty). This is recorded here per CLAUDE.md's "sweep changed files for superseded wording" spirit and because it is exactly the class of mistake the project's own falsification discipline exists to catch before it is reported as done.

## What this means for enemies specifically

`EnemyController` registers **itself**, gated on its own `driven_externally`, from a deferred call in its own `_ready()`. Because `driven_externally` now lives only as a runtime flip (not a `.tscn` default), it is `true` only for the three hand-placed enemies `PrototypeIntegration` reaches by `NodePath`. A **Wave-Director-spawned enemy created after `PrototypeIntegration`'s own `_ready()` has already returned is never reached by that flip** and keeps `driven_externally = false` — i.e. it keeps self-driving via its own `_physics_process()`, exactly the pre-existing behaviour, rather than joining SimLoop's step 3. This is a **required seam**, not a silent gap: whichever task next owns `src/core/entity_spawner.gd` / `src/director/wave_director.gd`'s own spawn call site would need to set `driven_externally = true` and call `SimLoop.register(SimLoop.Step.ENEMY_AI_AND_MOVEMENT, instance)` at the moment a new enemy is actually spawned, mirroring what `PrototypeIntegration` does for the hand-placed three. I did not attempt this myself: both files are outside this task's write scope, and `Pool.acquire()`'s own factory-override semantics (a pool with an empty free list uses the given factory; a non-empty free list reuses whatever generic instance is already there, **regardless of the archetype requested**) raise a further, pre-existing question about whether a reused pooled enemy is even the right archetype — outside this task to investigate or fix, named here only because it bears on whether "re-register on reuse" would even be meaningful without that being resolved first.

## Interpretation named, not silently assumed: step 6 has no registrant

docs/20 assigns "wind-up completion and contact ticks" to step 6, separately from step 3's "enemy AI and movement." `EnemyController.physics_step()` (registered at step 3) already runs `_process_attack_cycle()` — the wind-up/contact-tick logic — at the end of the same call. Splitting this into a second, independently-registered step-6 method would be a redesign of `enemy_controller.gd`'s single-method shape, which this task's brief forbids ("do not redesign components"). `_step_06_windup_completion_and_contact_ticks()` still runs `_run_step(Step.WINDUP_AND_CONTACT_TICKS, delta)` (currently against an empty registration list — a harmless no-op) so the step exists and is named for a future registrant. Both the movement and the attack-cycle logic still resolve before step 7's hit queue regardless of which of the two steps' names is attached to the call, which is the property that actually matters for determinism; the deviation from docs/20's literal per-step split is recorded here rather than fixed by restructuring the controller.
