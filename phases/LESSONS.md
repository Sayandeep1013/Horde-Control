# Lessons Carried Between Phases

Patterns that must inform later phases: recurring failure types, estimates that ran over, tests that turned out unpassable, tools that misbehaved.

| Date | Phase | Lesson | Applies to |
| --- | --- | --- | --- |
| 2026-09-17 | 00 | Prove a tooling config change works BEFORE applying it. Pinning both MCP servers to commit-pinned git specs looked correct and cost a whole session of dead tooling, because npx on this machine cannot install any git spec. The second attempt piped a real MCP initialize request into each built server first, then changed the config | Any phase that changes MCP config, engine version, addon versions, or the test harness |
| 2026-09-17 | 00 | npx cannot install commit-pinned git specs here (GitFetcher/Arborist error), and packages whose build/ is gitignored expose their binary only through the npm tarball. Pin by cloning at the commit and building locally, then run the built entry point with node | P0.5/docs/28, and any later tool pinning |
| 2026-09-17 | 00 | Everything under the Godot project root is a resource. The first export packed the built MCP servers into the game - 11.2 MB pck for an empty scene. .gdignore in a subtree makes the engine skip it entirely; export filters are the weaker fix | Every phase that exports a build, and anything that adds tooling under the project root |
| 2026-09-17 | 00 | Tools that generate Godot config cannot be trusted on version fields: the MCP generator writes config/features 4.4 regardless of the running engine, and that stray value also made a skill pack instruct every agent to target 4.4. Author project.godot by hand and assert the recorded value in a test | P0.6, P1.x, and any task that writes project settings |
| 2026-09-17 | 00 | A passing acceptance test proves nothing until it has been made to fail AGAINST ITS OWN MECHANISM. The Settings check was first falsified twice, on a layer name and the features array, and a reviewer then showed it still passed with exit 0 on a project whose entire display block was deleted and whose movement key was rebound: both original falsifications hit assertions that were already the strongest, while the check asserted existence rather than value everywhere else. Rewritten to assert effective values and exact sets, then falsified ten ways including rogue entries. The rule is: break the assertion you are least confident in, and break the class of thing the check is meant to catch, not the easiest target | Every task whose exit criterion names an acceptance test |
| 2026-09-17 | 00 | Spot-check subagent output rather than accepting the report. Reading 3 of 26 generated stubs found a rendering defect (F-01) that the agent's own summary described as complete | Every phase that delegates bulk writing or implementation to subagents |
| 2026-09-17 | 00 | Long-running subagents can stop without writing their report. Their working artifacts are still on disk and worth salvaging before re-running: the interrupted E0.1 agent had already proven the CLI rows and disproved the 4.7.1 headless stall bug | Any phase delegating long evidence-gathering runs |
| 2026-09-18 | 00 | Review rigor is set by risk, not applied uniformly, and any narrowing is decided in advance and written down. Phase 00 ran a full reviewer panel and it earned its cost; iteration 2 then cut the panel without recording it, and the phase reviewer named five per-task defects that slipped through as a result | Every phase gate: code and gate phases keep one critical agent per task plus a phase reviewer; documentation-only phases take a spot-check (decision D83) |
| 2026-09-18 | 00 | A tool that reports success is not evidence the effect happened, and a document that cites evidence is not evidence either. Three separate findings came from reading the artifact back: a property silently not written, a test that passed on a broken project, and a 1.0.0 document citing a path that did not exist | Every phase: verify by reading back the artifact, and cite only paths that exist in the repository |
| 2026-09-18 | 01 | A check that consumes another tool's exit code needs falsifying too, not just the tool. P0.7 verified all of gdUnit4's exit codes and then wrote a runner script that reported PASS after executing zero tests, on two paths: a missing executable left a stale `$LASTEXITCODE` that both guards read as success, and gdUnit4 itself exits 0 on "No test cases found". The lesson from Phase 00 was applied thoroughly one task over, to the Schema check, and not at all here | Every phase that wraps a tool in a script, and anything CI consumes |
| 2026-09-18 | 01 | A validator that derives its expectations from the thing it validates cannot detect an omission. The Schema check asked each script what fields it had, so deleting a field removed it from script and sample at once and the check stayed green. The fix is an independent manifest transcribed from the source document, so the two can disagree. Ask of any check: what would it take for this to pass on work that was never done? | Every acceptance test, especially schema, contract, and config checks |
| 2026-09-18 | 01 | "Cannot be reproduced here" is a claim requiring an experiment, exactly like a root cause. An exit code was recorded twice as unreproducible on the stated ground that testing it would mean destroying the project's cache; a reviewer reproduced it in two minutes by copying the project to a scratch directory, and the ledger had itself named that method before declining to use it. This is Phase 00's F-08 lesson recurring inside the phase that carried it forward | Every phase: the rule covers negative claims as well as causes |
| 2026-09-18 | 01 | Re-read already-written delegation scopes whenever a decision lands mid-phase. A decision required a pin in docs/28, but the delegation prompt for that task had already forbidden `docs/` edits, so the implementer was structurally unable to satisfy a phase exit condition and nothing in its brief would have shown it that. Two of the phase's eight Major findings were against the orchestrator, not the implementers | Any phase that takes decisions while delegated work is in flight |
| 2026-09-18 | 01 | Check the record's structure mechanically, not by reading it - and check more than the column count. LEDGER.md rendered plausibly while its Status column was missing from every row; a column count caught that and caught the botched first repair. But the same file then broke twice more in ways a column count **cannot** see: rows inserted above the table header, rendering as a detached headerless table, and rows whose Status and Evidence cells were in each other's positions. Both were 7 columns and both passed the check. The check has to assert that every row sits below a header, has the right column count, and that the status cell actually holds a status word | Every phase: before the gate, verify each table in the phase record for row position, column count, and column identity - not just width |
| 2026-09-18 | 01 | Freeze the tree when the gate opens, or re-brief the reviewers with a diff. Recorded after iteration 1, then broken worse in iteration 2: the phase reviewer watched five separate edits land mid-review, got a **false failure** from a check because a parallel reviewer had renamed a method in the live tree, and had to reconstruct the committed tree in a scratch directory to review at all. No reviewer was told the tree had moved. Writing the lesson down did nothing; the gate needs a mechanism - review a commit, a tag, or an exported copy, not the working tree. Iteration 3 applied that and it held for every reviewer. But the rule as first written closes reading and not writing: a reviewer falsifying a check **mutates** the shared tree, which is exactly the event that gave iteration 2 its false failure, and it happened again under the fixed rule without breaching it | Every review gate: reviewers read a frozen tree AND falsify against an exported copy of it rather than the shared working directory, and any mid-gate change is either deferred or announced to every open reviewer |
| 2026-09-18 | 01 | Under-claiming is cheap and it compounds. Every place this phase wrote "not reproduced", "a tested observation, not an inferred one", or "almost certainly, not established" survived review intact, and the phase reviewer counted seven such instances in the phase's favour against a single overclaim. The one overclaim - "doc 02 carries no numerals at all" - was false in a way that cost nothing substantively and still had to be corrected | Every phase record and every report to the author |
| 2026-09-18 | 01 | Any check whose green result is used as evidence must itself be falsified, including the ones that check the record rather than the code. Phase 01's ledger-integrity check read the wrong column, could never have returned anything but "no open Majors", and that result was reported to the author twice as proof the phase cleared its bar. Two sibling instances in the same phase: a schema check that asked the script under test what fields to expect, and a CI guard that matched negatively on output and so passed whenever the output was lost. The shape is always the same - the check derives its expectation from the thing it is checking, or it can only ever say yes | Every phase: before a check's result is cited as evidence, make it fail on purpose. This applies to checks over the phase record, not only over the product |

| 2026-09-19 | 02 | A green gdUnit4 summary is not evidence the engine was happy. gdUnit4's error count excludes Godot's own engine errors - measured, five `push_error` calls gave `0 errors` at exit 0 - and that blind spot hid a real dangling-reference bug in EntityRegistry for a whole phase. `tests/run_tests.ps1` now reads the engine channel and fails on it | Every phase: run tests through the script, never the raw gdUnit4 command, and read both results |
| 2026-09-19 | 03 | Setting up a mutation exposes the test as often as it exposes the code. Three times in one phase: a camera suite whose every case used a zero centre, so a clamp ignoring the arena centre was indistinguishable from a correct one; a projectile sweep test whose geometry the projectile's own collision radius already caught, so it passed with no sweep at all; and a visual test written specifically to catch missing sprites that passed against that very defect because a runtime-built telegraph node satisfied it. Each was caught while preparing the falsification, before anything was claimed | Every task whose exit criterion names an acceptance test: write the mutation first and ask what else could satisfy the assertion |
| 2026-09-19 | 03 | A mutation with zero effect is a finding about the implementation, not a weak test. Deleting the stuck-rule body-block exemption changed no test result because an earlier `in_attack_range` early return already short-circuited it: the clause was dead code, and removing it was the correct response | Every falsification pass: a mutation that changes nothing means the test is weak OR the clause does nothing - decide which before moving on |
| 2026-09-19 | 03 | A test suite that instantiates a scene is not evidence a human sees anything. All three enemies shipped with no sprite node at all while 353 tests stayed green, because the art was referenced only by a test that compares PNG files on disk. The question that found it was "which files reference this asset", not "does this asset load" | Every phase that wires art or UI: assert on the assembled scene a person actually launches, not only on components |
| 2026-09-19 | 03 | A test that cannot fail can hide inside a pair that looks thorough. Hardcoding the spawn seed root left "the same seed gives the same positions" green - a constant seed satisfies it trivially - and only the paired "a different seed changes at least one position" caught it | Every determinism, RNG, or caching test: write the negative case alongside the positive one |
| 2026-09-19 | 03 | Diagnose by experiment even when the first hypothesis is plausible. A suite exiting 101 on ~2000 orphans looked exactly like the object pools' deliberately-alive released instances; clearing the pools moved the count from 2016 to 1928. The real cause was `remove_child()` in `after_test()`, which orphans every descendant at the instant gdUnit4 counts. Both the disproved and the real explanation are kept in the record | Every phase: this is the "never write root cause without an experiment" rule recurring, now with a negative result worth keeping |
| 2026-09-19 | 03 | Godot's own defaults beat the skill pack's documentation. `z_as_relative` accumulates through every relative CanvasItem ancestor and its actual 4.7.1 default is `true`, contradicting the installed skill's stated default; nesting the player and Tower under a common root for the first time pushed their projectiles from the Register's z 30 to an effective 80 and 55 | Every task that follows a skill's stated engine default: verify it against the running engine before relying on it |
| 2026-09-20 | 03 | Hand someone a fixture and call it a prototype, and the verdict is about the missing frame rather than the thing being tested. The P2.7 feel check was handed over as "the prototype is playable" when what was playable was three hand-placed enemies in an empty box - by P2.7's own definition a feel-check fixture. The absence of waves was the documented Phase 04 boundary and the author met it as a surprise. Setting that expectation was the orchestrator's job | Every handover to the author: state what is deliberately absent before they play it, not after |
| 2026-09-20 | 04 | In a pooled system, object identity is not a stable test subject. A merge test that asserted a Node reference had disappeared from tracking was unsound, because the spawner can hand the just-freed instance straight back for the very next spawn in the same cascade. Assert on data - position, value, count - not on which object it is | Every test over pools, spawners, or anything that recycles instances |
| 2026-09-20 | 03 | A shared scene is shared: a mode flag belongs to whoever assembles the scene, not to the scene file. Baking `driven_externally = true` into `player.tscn` and the enemy scenes broke three suites that instantiate those same scenes directly and rely on self-driving with no SimLoop present. Flipping the export at runtime from the composition root touched only the wired instances and left the scene files untouched | Every task that adds a mode, debug or injection flag to an entity used by both the game and its tests |
| 2026-09-20 | 03 | A fix the orchestrator applies needs falsifying exactly like a delegated one, and a fix written against a single reported symptom tends to have no coverage at all. Adding the five missing SimLoop dispatch calls looked complete and was caught only by removing one again: seven candidate suites stayed green. The repair that held was to make the rule uniform - every step dispatches - and to assert it by iterating the enum rather than a hand-written list, so the next step added cannot fall out of it | Every fix, including the orchestrator's own; and prefer a test that derives its cases from the structure over one that lists them |
| 2026-09-20 | 03-05 | **Six findings in two phases have the same shape: a correct, tested component that nothing in the assembled scene ever calls.** Invisible enemies with 353 tests green (F03-27); the Pressure Metric not reaching the overlay (F04-04); stuck-enemy drops never connected (F04-11); the pickup system's NodePaths unset (F04-12); the upgrade system's four NodePaths unset (F05-07); the Draft scene never instantiated (F05-15). Component suites cannot see it by construction. The counter-measure is a single owned integration task whose assertions run against the scene a human launches, and which asserts the wiring itself - that each NodePath resolves and each signal has a connection | Every phase from here: budget the integration pass as its own task with its own tests, not as the last hour of a feature task |
| 2026-09-20 | 05 | A test that imports its expectation from the code under test cannot detect a change to that code. `console_rules_test.gd` declared `const DWELL = Console.OPEN_DWELL_SECONDS`, so zeroing the dwell moved the expectation with it and all sixteen cases stayed green under a mutation aimed straight at them. Expectations are transcribed from the owning document as independent literals - the same repair Phase 01's schema check needed for the same reason | Every test: if the code changes and the expectation changes with it, the test asserts only that the code equals itself |
| 2026-09-20 | 05 | **A logical range check and a physical collision shape are two different numbers, and nothing makes them agree.** Enemies gated their whole attack cycle on the Register's `reach_or_range_px` (20 px) while their hitbox was hard-coded to `body_radius + 6 px`, leaving a 14 px band in which the AI attacked on schedule and the `Area2D` shapes never touched - so melee enemies could not damage the Tower at all, and every test that asserted the attack cycle stayed green. Found only by parking one real enemy at a distance its own code called in-range and counting landed hits | Every attack, pickup, interaction or trigger radius: assert that the physical shape covers the logical gate, or derive one from the other |
| 2026-09-20 | 05 | **A test harness that builds its own dependencies can differ from the game in a way that makes every measurement through it meaningless, while every assertion in it still passes.** The teaching-Siege harness built an `EntitySpawner` with no container paths; `Pool` only parents an instance when it has a container, so every enemy it spawned sat outside the scene tree and outside the physics world, and the Tower measured full health in every seed because nothing was ever there. Three separate tuning measurements were taken through it. Found by changing a value and watching the result not move at all | Any harness that constructs a system the real scene also constructs: diff the harness's setup against the real scene's node, or build the harness from that scene. And treat a zero-effect change as a disconnection until proved otherwise |
| 2026-09-20 | 05 | **Wait on the frame type the code under test actually runs in.** A HUD sync living in `_process` was tested with `await get_tree().physics_frame`; it passed in one position in the file and failed in another, which read as test-order dependence and cost two wrong hypotheses - a leaked pause reason, then a dangling registry entry - before the mismatch was found. `physics_frame` does not guarantee a `_process` call | Every test that waits for a frame: check whether the behaviour is in `_process` or `_physics_process` first |
| 2026-09-20 | 05 | **A NodePath written from the wrong frame of reference resolves to nothing, silently, and no component test can see it.** Six exports on nodes sitting BESIDE the gameplay root were authored as if they sat inside it (`Main/Tower` instead of `../Main/Tower`); the Console would never have had a Tower, player, upgrade catalogue or camera. The scene's own comment beside those nodes said they were siblings. Caught on the first run of a suite that walks the assembled scene and resolves every set NodePath | Assert, once, generically, that every set NodePath in the shipped scene resolves - it costs one test and covers every node wired afterwards |

Rows are captured as they occur rather than at phase close, so they are available to the next phase immediately. Phase 00 is built and reviewed, its closure the designer's decision; Phase 01 has been through two review iterations.

A caution about this file, earned in Phase 01: a lesson recorded here is reliably applied to the artifact it was learned on and reliably **not** generalised one artifact over. Phase 01 applied "a check must be falsified" thoroughly to its schema check and not at all to the script consuming its exit codes; then, during the very gate that recorded three new lessons, broke all three of them. When reading these rows at phase entry, the useful question is not "did we do this" but "where else does this apply that we have not looked".
