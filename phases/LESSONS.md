# Lessons Carried Between Phases

Patterns that must inform later phases: recurring failure types, estimates that ran over, tests that turned out unpassable, tools that misbehaved.

| Date | Phase | Lesson | Applies to |
| --- | --- | --- | --- |
| 2026-09-17 | 00 | Prove a tooling config change works BEFORE applying it. Pinning both MCP servers to commit-pinned git specs looked correct and cost a whole session of dead tooling, because npx on this machine cannot install any git spec. The second attempt piped a real MCP initialize request into each built server first, then changed the config | Any phase that changes MCP config, engine version, addon versions, or the test harness |
| 2026-09-17 | 00 | npx cannot install commit-pinned git specs here (GitFetcher/Arborist error), and packages whose build/ is gitignored expose their binary only through the npm tarball. Pin by cloning at the commit and building locally, then run the built entry point with node | P0.5/docs/28, and any later tool pinning |
| 2026-09-17 | 00 | Everything under the Godot project root is a resource. The first export packed the built MCP servers into the game - 11.2 MB pck for an empty scene. .gdignore in a subtree makes the engine skip it entirely; export filters are the weaker fix | Every phase that exports a build, and anything that adds tooling under the project root |
| 2026-09-17 | 00 | Tools that generate Godot config cannot be trusted on version fields: the MCP generator writes config/features 4.4 regardless of the running engine, and that stray value also made a skill pack instruct every agent to target 4.4. Author project.godot by hand and assert the recorded value in a test | P0.6, P1.x, and any task that writes project settings |
| 2026-09-17 | 00 | A passing acceptance test proves nothing until it has been made to fail AGAINST ITS OWN MECHANISM. The Settings check was first falsified twice, on a layer name and the features array, and a reviewer then showed it still passed with exit 0 on a project whose entire display block was deleted and whose movement key was rebound: both original falsifications hit assertions that were already the strongest, while the check asserted existence rather than value everywhere else. Rewritten to assert effective values and exact sets, then falsified ten ways including rogue entries. The rule is: break the assertion you are least confident in, and break the class of thing the check is meant to catch, not the easiest target | Every task whose exit criterion names an acceptance test |
| 2026-09-17 | 00 | Spot-check subagent output rather than accepting the report. Reading 3 of 26 generated stubs found a rendering defect (F-01) that the agent's own summary described as complete | Every phase that delegates bulk writing or implementation to subagents |
| 2026-09-17 | 00 | Long-running subagents can stop without writing their report. Their working artifacts are still on disk and worth salvaging before re-running: the interrupted E0.1 agent had already proven the CLI rows and disproved the 4.7.1 headless stall bug | Any phase delegating long evidence-gathering runs |

| 2026-09-18 | 00 | Review rigor is set by risk, not applied uniformly, and any narrowing is decided in advance and written down. Phase 00 ran a full reviewer panel and it earned its cost; iteration 2 then cut the panel without recording it, and the phase reviewer named five per-task defects that slipped through as a result | Every phase gate: code and gate phases keep one critical agent per task plus a phase reviewer; documentation-only phases take a spot-check (decision D83) |
| 2026-09-18 | 00 | A tool that reports success is not evidence the effect happened, and a document that cites evidence is not evidence either. Three separate findings came from reading the artifact back: a property silently not written, a test that passed on a broken project, and a 1.0.0 document citing a path that did not exist | Every phase: verify by reading back the artifact, and cite only paths that exist in the repository |

| 2026-09-18 | 01 | A check that consumes another tool's exit code needs falsifying too, not just the tool. P0.7 verified all of gdUnit4's exit codes and then wrote a runner script that reported PASS after executing zero tests, on two paths: a missing executable left a stale `$LASTEXITCODE` that both guards read as success, and gdUnit4 itself exits 0 on "No test cases found". The lesson from Phase 00 was applied thoroughly one task over, to the Schema check, and not at all here | Every phase that wraps a tool in a script, and anything CI consumes |
| 2026-09-18 | 01 | A validator that derives its expectations from the thing it validates cannot detect an omission. The Schema check asked each script what fields it had, so deleting a field removed it from script and sample at once and the check stayed green. The fix is an independent manifest transcribed from the source document, so the two can disagree. Ask of any check: what would it take for this to pass on work that was never done? | Every acceptance test, especially schema, contract, and config checks |
| 2026-09-18 | 01 | "Cannot be reproduced here" is a claim requiring an experiment, exactly like a root cause. An exit code was recorded twice as unreproducible on the stated ground that testing it would mean destroying the project's cache; a reviewer reproduced it in two minutes by copying the project to a scratch directory, and the ledger had itself named that method before declining to use it. This is Phase 00's F-08 lesson recurring inside the phase that carried it forward | Every phase: the rule covers negative claims as well as causes |
| 2026-09-18 | 01 | Re-read already-written delegation scopes whenever a decision lands mid-phase. A decision required a pin in docs/28, but the delegation prompt for that task had already forbidden `docs/` edits, so the implementer was structurally unable to satisfy a phase exit condition and nothing in its brief would have shown it that. Two of the phase's eight Major findings were against the orchestrator, not the implementers | Any phase that takes decisions while delegated work is in flight |
| 2026-09-18 | 01 | Check the record's structure mechanically, not by reading it - and check more than the column count. LEDGER.md rendered plausibly while its Status column was missing from every row; a column count caught that and caught the botched first repair. But the same file then broke twice more in ways a column count **cannot** see: rows inserted above the table header, rendering as a detached headerless table, and rows whose Status and Evidence cells were in each other's positions. Both were 7 columns and both passed the check. The check has to assert that every row sits below a header, has the right column count, and that the status cell actually holds a status word | Every phase: before the gate, verify each table in the phase record for row position, column count, and column identity - not just width |
| 2026-09-18 | 01 | Freeze the tree when the gate opens, or re-brief the reviewers with a diff. Recorded after iteration 1, then broken worse in iteration 2: the phase reviewer watched five separate edits land mid-review, got a **false failure** from a check because a parallel reviewer had renamed a method in the live tree, and had to reconstruct the committed tree in a scratch directory to review at all. No reviewer was told the tree had moved. Writing the lesson down did nothing; the gate needs a mechanism - review a commit, a tag, or an exported copy, not the working tree | Every review gate: reviewers read a frozen tree, and any mid-gate change is either deferred or announced to every open reviewer |
| 2026-09-18 | 01 | Under-claiming is cheap and it compounds. Every place this phase wrote "not reproduced", "a tested observation, not an inferred one", or "almost certainly, not established" survived review intact, and the phase reviewer counted seven such instances in the phase's favour against a single overclaim. The one overclaim - "doc 02 carries no numerals at all" - was false in a way that cost nothing substantively and still had to be corrected | Every phase record and every report to the author |

Rows are captured as they occur rather than at phase close, so they are available to the next phase immediately. Phase 00 is built and reviewed, its closure the designer's decision; Phase 01 has been through two review iterations.

A caution about this file, earned in Phase 01: a lesson recorded here is reliably applied to the artifact it was learned on and reliably **not** generalised one artifact over. Phase 01 applied "a check must be falsified" thoroughly to its schema check and not at all to the script consuming its exit codes; then, during the very gate that recorded three new lessons, broke all three of them. When reading these rows at phase entry, the useful question is not "did we do this" but "where else does this apply that we have not looked".
