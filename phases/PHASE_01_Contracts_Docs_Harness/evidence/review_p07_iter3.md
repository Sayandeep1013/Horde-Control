## 3. New findings

### NEW-6 - Major: the four-code distinction is now broken for two of the four codes

`run_tests.ps1:134-157` places guard 3 **before** the exit-code switch. A real gdUnit4 exit 103
and a real gdUnit4 exit 1 both print no `Executed test cases` line - 103 aborts at the headless
check, and exit 1 never loads `GdUnitCmdTool.gd` at all. So both are swallowed by guard 3 and
reported as **exit 1** with a message naming three causes, none of which occurred (C7, C8).

This contradicts a requirement stated in three places, all of which still say otherwise:

- `NEXT_SESSION.md:51` - "Four exit codes, and **CI must distinguish all four**: 0 pass, 100
  assertion failure, 103 `--ignoreHeadlessMode` missing, 1 import pass not run."
- `run_tests.ps1:14-27` - "Maps each of the four exit codes this project has verified into a
  distinct, human-readable message, and exits with that same code so a caller (CI or a human) can
  **distinguish all four without parsing output**", and specifically "103 misconfigured - ...
  seeing 103 means the invocation below was changed or bypassed". You can no longer see 103.
- `docs/28_AI_Development_Workflow.md:129` - the sentence **added this iteration** to close
  F01-38: "That script runs the import pass, **maps all four codes to distinct messages and exit
  statuses** ...". C7 falsifies that sentence directly.

I weigh this as Major, and I want to be exact about why it is a **lesser** Major than iteration
2's: it never reports success wrongly. Everything here fails closed. What it does is (a) break a
thrice-stated "must", (b) write a demonstrably false claim into a permanent 1.1.0 document in the
same iteration as the change that falsified it - which is the "sweep changed files for superseded
wording" rule broken on the very file being swept - and (c) hand a later phase a misleading CI
signal in exactly the scenario the 103 branch was written for. The LEDGER's F01-36 Resolution
records the fix and does not mention the trade-off, so nothing in the record flags it either.

**Smallest fix**: require the anchor only when `$testExit -eq 0`, and let 100/103/1 fall through
to the switch. That keeps the fail-closed property exactly where it matters - a claimed pass - and
restores all four codes. Two lines.

### NEW-7 - Minor: the typo'd path, the case this whole finding exists for, now gets a diagnostic naming three causes that did not occur

D6 and D7. gdUnit4 aborts with `No test cases found, abort test run!` **before** the STOP event
that prints the summary, so it never emits `Executed test cases : (0/0)`. The branch that names
the right cause - "Zero tests executed is never a pass - check the path for a typo"
(`run_tests.ps1:154-157`) - is therefore **dead code for real gdUnit4**; I could only reach it
with a forged shim (C1). What an operator with a typo'd `-TestPath` actually gets is the generic
message blaming lost stdout, an unwritable TEMP directory, or a non-Godot binary - while
`No test cases found, abort test run!` is sitting in the output two lines above.

This is the same defect class as my predecessor's NEW-2 ("naming a cause that did not happen"),
fixed in one place and reintroduced in another by the same iteration. The fix is cheap and
weakens nothing: keep the negative match as an *additional diagnostic* alongside the positive
assertion. They are not alternatives - the positive form decides the verdict, the negative form
writes the message.

### NEW-7a - Minor: a genuinely passing suite now reports failure when TEMP is unusable

Attack C. With `TEMP`/`TMP` pointed at a nonexistent drive, the default run - valid path, real
Godot - exits **1**. C-proof shows the suite itself exits 0 with `Executed test cases : (1/1)`.
This is a behaviour change from iteration 2, where the same conditions printed `PASS`; the new
direction is the safe one and the message does list "an unwritable TEMP directory" among the
causes, which is why this is Minor rather than more. But it is a false failure on an environment
condition rather than an operator mistake - containers, service accounts, restricted runners -
and the run is also noisy: `$SuiteLog` becomes `$null` when `Join-Path` throws on a missing drive,
which produces three unhandled `ParameterBindingValidationException`s (`run_tests.ps1:100`,
`:125`, `:127`) and silently redirects the entire suite output to nowhere.

**Root cause worth naming**: the script routes gdUnit4's output through a file in the system TEMP
directory for no reason I can find. Capturing it in-process - `$suiteOutput = & $GodotPath ... 2>&1 |
Out-String` - removes the TEMP dependency, the null-`$SuiteLog` path, the stale-file question in
observation (b), and the cleanup step, all at once.

### Observations - not defects, recorded because they are load-bearing and undocumented

**(a) The anchor is stable, and safe for a reason nobody chose.**
`build_executed_test_case_msg` is at `GdUnitConsoleTestReporter.gd:182-185`, called
unconditionally from the `GdUnitEvent.STOP` handler (`:44`), and the CI runner always constructs
that reporter (`GdUnitTestCIRunner.gd:108`). So the line is emitted by every run that reaches
STOP, in either of two forms - `(n/n)` when nothing is skipped, `(n/m), k skipped` otherwise - and
the regex matches both. The line is wrapped in a single ANSI colour span
(`ESC[38;2;233;150;122m ... ESC[0m`), so the escapes fall outside the match; if gdUnit4 ever
coloured per token, the regex would break silently. On locale: `-match` is case-insensitive by
default, which under `tr-TR` folds `I`/`i` differently - and the anchor happens to contain no `i`
or `I` at all, so the hazard does not apply. That is luck, not design. `\d` is
culture-independent, and the log is UTF-8 with BOM, so decoding is safe. F3 confirms all of this
empirically.

**(b) Guard 3 trusts a file without proof that this run wrote it.** E1 shows the script reading
and echoing a pre-seeded anchor it did not produce. The false green was prevented by the
`$null -eq $testExit` check two blocks earlier, which holds because `$global:LASTEXITCODE = $null`
is set before each invocation and a failed redirection means PowerShell never runs the command.
The guards compose correctly, but the ordering is doing real work and no comment says so.
Capturing in-process (NEW-7a) makes the question disappear.

**(c) `n` is the executed count, not a completeness check.** From the source, the first number is
`total - skipped`. A suite where 49 of 50 cases are skipped prints `(1/50)` and the script reports
`PASS (exit 0): 1 test case(s) executed ... all passed` (C9). That is defensible - a skip is not a
failure - and the pass line does surface the count, which is a real improvement over iteration 2's
bare `PASS`. A fully skipped suite prints `(0/n)` and correctly fails closed. Recorded so nobody
later reads `n >= 1` as "the suite ran completely".
